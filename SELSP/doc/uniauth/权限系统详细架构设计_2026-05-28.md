# 权限系统详细架构设计

## 1. 设计目标

本设计面向 `SELSP` 下的 `uniauth` 权限系统，目标是构建一个：

- 统一认证
- 统一授权
- 可模块化扩展
- 可供多业务系统接入
- 与考勤系统业务边界解耦
- 与考勤数据库物理分离

的企业级轻量权限平台。

## 2. 设计原则

### 2.1 独立数据库原则
- 权限系统必须使用**独立数据库**
- 不与考勤系统共用表
- 不与考勤系统共用 schema
- 不与考勤系统混合落库

### 2.2 系统边界原则
- `uniauth` 是平台级权限中心
- `attendance` 是业务系统
- 权限中心负责：
  - 用户身份认证
  - Token 签发
  - 用户角色关系
  - 角色权限关系
  - 模块开关与模块授权
- 考勤系统负责：
  - 业务数据
  - 业务流程
  - 业务校验

### 2.3 业务解耦原则
- 考勤系统不得直接依赖权限库内部表结构
- 权限系统不得直接依赖考勤业务表
- 两者之间通过：
  - JWT
  - REST API
  - 受控用户上下文
 进行协作

### 2.4 插件化接入原则
- 考勤、财务、HR 等业务系统都视为接入模块
- 权限系统统一管理模块定义和模块权限
- 每个业务系统只声明自己的资源和动作，不复制整套权限框架

## 3. 总体架构

## 3.1 逻辑分层

```text
前端系统（SELVUE / 其他前端）
        |
        v
权限中心 API（uniauth）
  - 登录认证
  - Token 刷新
  - 用户/角色/权限/模块管理
  - 当前用户授权信息下发
        |
        v
权限中心数据库（独立库）

业务系统 API（attendance / 其他系统）
  - 校验 JWT
  - 读取当前用户上下文
  - 判断是否具备业务操作权限
        |
        v
业务系统数据库（考勤库独立）
```

## 3.2 物理拆分

推荐物理形态：

### 方案 A：单应用进程，双数据源
- `SELSP` 内同时存在：
  - `attendance`
  - `uniauth`
- 但数据库拆成：
  - `attendance_db`
  - `uniauth_db`

适用于：
- 当前阶段快速落地
- 部署资源有限

### 方案 B：独立权限服务，独立业务服务
- `SELSP-uniauth`
- `SELSP-attendance`
- 两个进程、两个服务、两个数据库

适用于：
- 后续企业级扩展
- 多系统接入增多
- 权限中心需要单独扩展

### 当前推荐
当前阶段推荐：
- **代码上先做模块隔离**
- **数据库上立即独立**
- **部署上可先保留单进程双数据源**

也就是：
- 架构先按平台化设计
- 部署先按现实成本落地

## 4. 数据库架构设计

## 4.1 数据库拆分要求

权限系统数据库必须独立，例如：

- `uniauth_db`

考勤系统数据库保持独立，例如：

- `attendance_db`

禁止：
- 把权限表建在考勤库里
- 把考勤业务表建在权限库里
- 用一个 schema 混装所有系统数据

## 4.2 权限库核心表

推荐最小核心表如下：

### 4.2.1 用户表 `ua_user`
- 用户主键
- 登录账号
- 密码摘要
- 用户姓名
- 邮箱
- 手机号
- 状态
- 锁定标记
- 失效时间
- 创建时间
- 更新时间

### 4.2.2 角色表 `ua_role`
- 角色主键
- 角色编码
- 角色名称
- 角色描述
- 状态
- 创建时间
- 更新时间

### 4.2.3 权限表 `ua_permission`
- 权限主键
- 权限编码
- 权限名称
- 权限类型
  - menu
  - button
  - api
  - data
- 模块编码
- 资源标识
- 动作标识
- 状态
- 创建时间
- 更新时间

### 4.2.4 模块表 `ua_module`
- 模块主键
- 模块编码
  - `attendance`
  - `finance`
  - `hr`
- 模块名称
- 模块描述
- 启用标记
- 排序
- 创建时间
- 更新时间

### 4.2.5 用户角色关系表 `ua_user_role`
- 用户主键
- 角色主键
- 生效时间
- 失效时间

### 4.2.6 角色权限关系表 `ua_role_permission`
- 角色主键
- 权限主键

### 4.2.7 模块权限关系表 `ua_module_permission`
- 模块主键
- 权限主键

### 4.2.8 用户模块开通表 `ua_user_module`
- 用户主键
- 模块主键
- 启用标记

### 4.2.9 登录会话 / refresh token 表 `ua_login_session`
- 会话主键
- 用户主键
- refresh token 摘要
- 设备信息
- 登录 IP
- 过期时间
- 撤销标记

### 4.2.10 审计日志表 `ua_audit_log`
- 操作人
- 操作对象
- 操作类型
- 操作结果
- 请求路径
- 时间戳

## 4.3 考勤库保留范围
考勤库只保留：
- tenant
- workplace
- department
- employee
- shift template
- schedule
- 其他考勤业务表

考勤库中不应再新增：
- 用户账号表
- 角色表
- 权限表
- token 表
- 模块表

## 6. 接口架构设计

## 6.1 权限中心接口

推荐接口：

### 认证接口
- `POST /api/uniauth/auth/login`
- `POST /api/uniauth/auth/refresh`
- `POST /api/uniauth/auth/logout`
- `GET /api/uniauth/auth/me`

### 用户接口
- `GET /api/uniauth/users`
- `POST /api/uniauth/users`
- `PUT /api/uniauth/users/{id}`
- `PUT /api/uniauth/users/{id}/status`
- `PUT /api/uniauth/users/{id}/roles`
- `PUT /api/uniauth/users/{id}/modules`

### 角色接口
- `GET /api/uniauth/roles`
- `POST /api/uniauth/roles`
- `PUT /api/uniauth/roles/{id}`
- `PUT /api/uniauth/roles/{id}/permissions`

### 权限接口
- `GET /api/uniauth/permissions`
- `POST /api/uniauth/permissions`
- `PUT /api/uniauth/permissions/{id}`

### 模块接口
- `GET /api/uniauth/modules`
- `POST /api/uniauth/modules`
- `PUT /api/uniauth/modules/{id}`
- `PUT /api/uniauth/modules/{id}/status`

## 6.2 业务系统接入接口

业务系统本身不直接查权限库。

推荐方式：
- 前端先登录权限中心
- 获取 JWT
- 业务系统只校验 JWT 和权限声明

业务系统可使用：
- 用户 ID
- 用户名
- 模块列表
- 权限编码列表
- tenant 范围

作为当前请求上下文。

## 7. 鉴权流程设计

## 7.1 登录流程

1. 前端调用 `uniauth` 登录接口
2. 权限中心校验账号密码
3. 加载用户、角色、权限、模块
4. 签发 access token
5. 签发 refresh token
6. 返回用户权限快照

## 7.2 访问业务系统流程

1. 前端携带 JWT 调用考勤系统
2. 考勤系统拦截器解析 JWT
3. 校验签名、过期时间、模块权限
4. 写入当前用户上下文
5. controller / service 只读取上下文，不查权限库

## 7.3 动态菜单流程

1. 前端登录后获取当前用户可用模块和菜单权限
2. 根据权限动态渲染菜单
3. 页面按钮按权限编码显示/隐藏

## 8. 与考勤系统的解耦方式

## 8.1 数据解耦
- 权限数据在 `uniauth_db`
- 考勤数据在 `attendance_db`

## 8.2 代码解耦
- `attendance` 不直接访问 `uniauth` 的 DAO
- `attendance` 不直接操作权限表
- `uniauth` 不直接访问考勤业务 DAO

## 8.3 接口解耦
- 通过 JWT 承载权限结果
- 通过标准化上下文承载用户身份
- 不通过数据库跨库直接联表实现权限判断

## 8.4 模块解耦
- `attendance` 只声明自己的权限资源
- `uniauth` 统一管理这些资源
- 新业务系统接入时沿用同样方式

## 11. 部署建议

## 11.1 第一阶段
- 单仓库
- 单应用
- 双数据源

优点：
- 上线快
- 代码可共用

## 11.2 第二阶段
- 权限中心独立服务
- 考勤系统独立服务

优点：
- 更适合多系统接入
- 更适合扩容

## 12. 当前落地建议

针对当前 `SELSP`，推荐这样落地：

1. 在 `com.sp.selfsp` 下新增 `uniauth` 模块
2. 先采用单进程双数据源
3. 数据库立即独立为 `uniauth_db`
4. JWT 与 RBAC 先做最小闭环
5. `attendance` 改为只消费 JWT 上下文
6. 后续再把 `uniauth` 独立服务化

## 13. 最终结论

权限系统必须：
- 独立数据库
- 独立权限模型
- 独立认证与授权逻辑

考勤系统只作为：
- 权限系统的接入业务模块

而不是：
- 权限数据的持有者

这是当前需求下最稳的设计方式，也是后续扩展到财务、HR、多模块平台的前提。
