# 日本通用勤怠排班系统详细设计文档

> 适用工程架构：SELATTENDANCE / SELSP + SELVUE + SELTHEME + uniauth  
> 系统定位：日本向け汎用勤怠・シフト管理システム  
> 版本：v2.0（补充极限用户友好前端设计与阶段规划）  
> 文档用途：用于系统设计、数据库建模、前后端开发、Codex/AI 开发任务拆分

---

## 1. 项目背景

本系统用于日本企业、学校、教室、补习机构、服务行业等场景中的员工勤怠管理。

系统需要支持：

- 员工管理
- 班次模板管理
- 排班管理
- 接入第三方打卡系统
- 接收打卡数据
- 手动打卡
- CSV 导入打卡
- 日次勤怠计算
- 月次勤怠汇总
- 迟到、早退、缺勤、缺卡判断
- 加班、深夜、休日出勤计算
- 有休管理
- 审批修正
- 月结锁定
- 工资系统导出

系统核心思想：

```text
排班是计划
打卡是事实
计算是结果
审批是修正
月结是锁定
导出是工资依据
```

## 3. 技术架构

本设计必须基于当前工程 `C:\opt\workspace\SEL\SELATTENDANCE` 落地，不重新引入另一套工程架构。

工程边界如下：

```text
SELATTENDANCE
├── DOC        架构、交付、规范文档
├── SELSP      后端 Spring Boot 工程
├── SELVUE     前端 Vue 3 + Vite 工程
├── SELTHEME   主题工程
└── SELFMEMORY 执行文档、方案与过程沉淀
```

设计口径：

- 后端业务模块统一落在 `SELSP`，其中勤怠域统一收口到 `com.sp.selfsp.attendance.*`。
- 权限域统一落在独立 `uniauth` 模块 / 命名空间，禁止继续把用户、角色、权限表直接并入勤怠业务表。
- 前端新增页面、组件、状态和接口服务统一落在 `SELVUE`，并遵循“宿主 + 子工程”结构。
- 主题变量、主题样式和可复用视觉资产优先复用 `SELTHEME`。
- 文档、接口、数据库、启动说明优先同步到 `SELATTENDANCE/DOC` 或业务工程自身 `doc` 目录。
- 本系统是中日双语勤怠系统，所有页面文案、菜单、按钮、状态、错误提示和导出标题必须支持中文 / 日语一键切换。
- 第一版继续优先复用当前模板能力，但权限中心已经单独成型为 `uniauth` 设计域，允许在该域内单独引入 JWT / RBAC 所需能力。

### 3.1 技术选型

| 层级 | 技术 |
|---|---|
| 模板工程 | SELATTENDANCE |
| 后端工程 | SELSP |
| 后端基线 | Java + Spring Boot 3.5.x |
| 数据访问 | MyBatis 3.x |
| 勤怠数据库 | 开发态 H2 2.x，正式态独立 `attendance_db` |
| 权限数据库 | 开发态独立 H2 2.x，正式态独立 `uniauth_db` |
| 前端工程 | SELVUE |
| 前端基线 | Vue 3 + Vite + Composition API |
| 接口访问 | 原生 Fetch 或统一 request 包装 |
| 主题工程 | SELTHEME |
| 样式体系 | CSS Variables + 模板主题样式 |
| 测试 | JUnit 5 / MockMvc / JaCoCo / Vitest / Playwright |
| 文件导入 | CSV 文本解析 |
| 文件导出 | CSV 文本生成 |
| 国际化 | 前端本地 i18n 字典 + 后端错误码 / 状态码映射 |
| 启动方式 | SELATTENDANCE 当前已定义的前端、后端、全套启动脚本模式 |

### 3.2 禁止额外增加的外部依赖

勤怠域第一版不得新增以下依赖或基础设施：

- 不新增 Redis、RabbitMQ、Kafka 等中间件。
- 不新增 Docker 作为本地开发必需条件。
- 不新增 Element Plus、Bootstrap 等 UI 组件库。
- 不新增 Apache POI、EasyExcel 等 Excel 处理库。
- 不在 `attendance` 业务模块内直接引入 Spring Security 侵入式鉴权逻辑。
- 不新增 vue-i18n 等前端国际化库；第一版使用工程内本地字典和组合式状态完成中日切换。

补充约束：

- `attendance` 与 `uniauth` 的数据库必须物理分离，禁止共表、共 schema 混用。
- `attendance` 服务可以消费 `uniauth` 的 JWT / 用户上下文，但禁止反向让 `uniauth` 依赖勤怠业务表。
- 本地开发允许单进程双数据源，正式部署优先按独立库边界部署。

## 4. 系统整体架构

```text
SELVUE 宿主前端
    ↓
attendance 子工程 / memory 子工程
    ↓
Vite 开发代理 /api
    ↓
SELSP Spring Boot REST API
    ↓
attendance Controller / Service / DAO
    ↓
勤怠计算引擎
    ↓
attendance_db
    ↑
    │ 用户上下文 / 权限码
    │
uniauth 权限中心
    ↓
uniauth_db
    ↓
外部打卡系统 / CSV / Webhook / 手动打卡
```

说明：

- 开发态前端请求默认使用同源 `/api`，由 `SELVUE/vite.config.js` 代理到 `SELSP` 本地后端。
- `SELVUE` 当前已经是“宿主 + 子工程”结构，宿主负责工程发现与切换，`attendance` 只是其中一个业务工程。
- 勤怠业务当前仍以 `SELSP` 单应用形式运行，但权限中心设计上已经独立为 `uniauth`，并要求使用独立数据库。
- 勤怠测试使用独立 `application-test.properties` 与 H2 内存测试库，不能再隐式复用主配置。
- DAO 与 SQL 映射沿用 `com/sp/selfsp/**/dao/mapper/*.xml` 的 MyBatis 映射规则。
- 中文 / 日语切换状态由前端统一维护，后端只返回稳定业务码、状态码、枚举码和必要参数，不返回硬编码页面文案。
- CSV 导入导出使用 UTF-8，导出标题根据当前语言生成中文或日语。

### 4.1 数据流

```text
管理员维护员工资料
    ↓
管理员创建班次模板
    ↓
管理员给员工排班
    ↓
员工或第三方系统产生打卡记录
    ↓
系统保存原始打卡数据
    ↓
系统根据排班和打卡记录计算日次勤怠
    ↓
系统生成异常
    ↓
员工/管理员提交修正或审批
    ↓
重新计算勤怠
    ↓
生成月次汇总
    ↓
月结锁定
    ↓
导出工资数据
```

## 5. 后端工程结构

后端必须复用 `SELSP` 结构，根包保持 `com.sp.selfsp`。当前实际落地口径是：勤怠业务统一放在 `com.sp.selfsp.attendance` 下，再按子域拆分 `bootstrap / tenant / workplace / department / employee / shifttemplate / schedule`，而不是继续把所有业务平铺到根包。

推荐包结构：

```text
com.sp.selfsp
├── SelfspApplication.java
├── common
│   ├── config
│   ├── util
│   └── web
│
├── attendance
│   ├── common
│   ├── domain
│   │   ├── in
│   │   └── out
│   ├── bootstrap
│   │   ├── controller
│   │   ├── service
│   │   ├── service/impl
│   │   └── dao
│   ├── tenant
│   │   ├── controller
│   │   ├── service
│   │   ├── service/impl
│   │   └── dao
│   ├── workplace
│   │   ├── controller
│   │   ├── service
│   │   ├── service/impl
│   │   └── dao
│   ├── department
│   │   ├── controller
│   │   ├── service
│   │   ├── service/impl
│   │   └── dao
│   ├── employee
│   │   ├── controller
│   │   ├── service
│   │   ├── service/impl
│   │   └── dao
│   ├── shifttemplate
│   │   ├── controller
│   │   ├── service
│   │   ├── service/impl
│   │   └── dao
│   └── schedule
│       ├── controller
│       ├── service
│       ├── service/impl
│       └── dao
│
└── uniauth
    ├── common
    ├── auth
    ├── user
    ├── role
    ├── permission
    └── tenant
```

后端约束：

- `common` 只放跨模块公共能力，不放具体勤怠业务逻辑。
- Controller 只负责 HTTP 协议收口和统一响应，不直接写业务规则。
- Service 负责业务编排、校验和事务边界。
- DAO 负责 SQL 与对象映射，XML 映射文件放在 `dao/mapper` 并随模板资源规则打包。
- 输入对象放 `domain/in`，输出对象放 `domain/out`，持久化或领域对象放 `domain`。
- 枚举必须返回稳定 code，中文和日语显示名交给前端字典或 `/api/i18n/messages` 响应。
- `attendance` 不直接维护用户、角色、权限表，统一依赖 `uniauth` 下发的身份与权限信息。
- `bootstrap` 只负责轻量首页壳数据，不再承担全量业务列表聚合。
- `schedule`、`employee` 等复杂子域优先通过独立 `service` 和 `dao` 保持边界，不允许重新合并成单体大模块。

```text
│       └── style.css

```

前端约束：

- 宿主层只保留 `main.js`、`App.vue`、`projects/index.js` 和真正公共的 `shared`，禁止在宿主层硬编码 `attendance` 或 `memory` 业务实现。
- 业务工程按 `src/projects/<project-id>` 安装，装上目录即发现，移除目录后宿主仍可启动。
- `shared/services/request.js` 负责公共请求桥接；业务工程自己的 `services` 只放该工程的 API 封装。
- `attendance/composables/workbench` 负责“轻量 shell + 分区 section 加载”状态编排，不再把整个工作台塞回一个大文件。
- `attendance/constants/i18nMessages.js` 放中文 / 日语本地字典，`shared/components/LanguageSwitch.vue` 负责语言切换。
- 所有菜单、按钮、列名、枚举显示、校验提示、空状态、导出标题都必须从字典读取，不允许在页面里硬编码单语言文案。
- 主题样式优先复用 `SELTHEME` 的 CSS Variables 和现有视觉语言，不新增 UI 组件库。
- 前端测试统一放在 `SELVUE/test`，先按工程拆 `attendance / memory / host / diagnostics`，再按 `unit / integration / e2e` 分层。
- 正式 `e2e` 默认通过项目自管脚本启动本地 `Vite` 服务并执行 `Playwright`，不再依赖 `webServer` 托管模式。

## 6.1 中日双语国际化设计

### 6.1.1 国际化目标

本系统面向日本勤怠业务，但开发、维护和部分运营场景需要中文说明，因此第一版必须内置中文 / 日语双语能力。

目标：

```text
一键切换中文 / 日语
刷新后保留语言选择
菜单、按钮、表头、状态、错误提示双语显示
CSV 导出标题跟随当前语言
后端返回稳定 code，前端负责展示语言
```

### 6.1.2 语言范围

第一版支持：

| 语言 code | 显示名称 | 用途 |
|---|---|---|
| zh-CN | 中文 | 开发、运营、中文客户演示 |
| ja-JP | 日本語 | 日本客户正式使用 |

默认语言：

- 首次进入系统默认 `ja-JP`。
- 用户切换后保存到 `localStorage.attendance_locale`。
- 若本地保存值非法，回退到 `ja-JP`。

### 6.1.3 前端字典结构

第一版不引入 `vue-i18n`，使用 `SELVUE/src/constants/i18nMessages.js` 管理本地字典。

```js
export const SUPPORTED_LOCALES = ['zh-CN', 'ja-JP']

export const I18N_MESSAGES = {
  'zh-CN': {
    menu: {
      dashboard: '首页',
      employees: '员工管理',
      shifts: '排班管理'
    }
  },
  'ja-JP': {
    menu: {
      dashboard: 'ホーム',
      employees: '従業員管理',
      shifts: 'シフト管理'
    }
  }
}
```

### 6.1.4 语言切换组件

`LanguageSwitch.vue` 负责：

```text
显示当前语言
点击后在 zh-CN / ja-JP 之间切换
把选择写入 localStorage
通知页面重新渲染所有字典文案
```

页面使用规则：

- 任何页面不得直接写 `首页`、`ホーム`、`保存`、`保存する` 等硬编码文案。
- 页面只读取 `t('menu.dashboard')` 或等价本地方法。
- 枚举显示统一通过 `t('enum.xxx.yyy')` 获取。
- 后端返回 `status=CALCULATED`，前端按语言显示为 `已计算` 或 `計算済み`。

### 6.1.5 后端国际化边界

后端不承担页面文案翻译职责，只承担稳定语义输出：

- 返回稳定错误码，例如 `EMPLOYEE_NOT_FOUND`。
- 返回稳定枚举值，例如 `CLOCK_IN`、`CLOCK_OUT`、`LATE`。
- 返回必要参数，例如 `{ "employeeCode": "E0001" }`。
- 可提供 `/api/i18n/messages` 返回服务端错误码和业务枚举的默认中日字典，但第一版也可以由前端本地字典直接覆盖。

禁止：

- 后端在业务响应里直接返回只适合一种语言的页面提示。
- 数据库存储菜单名、按钮名、页面标题等前端展示文案。
- 为了国际化新增外部翻译服务或第三方国际化依赖。

### 6.1.6 CSV 导入导出语言规则

CSV 导入：

- 第一版优先支持固定字段 code。
- 可兼容中文表头和日语表头，但最终必须映射成统一字段名。

CSV 导出：

- 导出内容使用 UTF-8。
- 文件名包含语言无关业务语义，例如 `attendance_monthly_2026-05.csv`。
- 表头根据当前语言生成。
- 枚举列根据当前语言显示中文或日语。

示例：

```text
zh-CN: 员工编号,姓名,年月,总工时,残业时间
ja-JP: 従業員番号,氏名,年月,総労働時間,残業時間
```

## 7.4.4 数据表：employee_work_rule

用于配置员工适用的勤怠规则。

```sql
CREATE TABLE employee_work_rule (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
```

## 8. 勤怠计算引擎设计

---

# 8.1 计算引擎总体设计

核心入口：

```java
public interface AttendanceCalculationService {

    AttendanceDaily calculateDaily(Long tenantId, Long employeeId, LocalDate workDate);

    AttendanceMonthly calculateMonthly(Long tenantId, Long employeeId, YearMonth yearMonth);

    void recalculateByPunchLog(Long tenantId, Long punchLogId);

    void recalculateByDateRange(Long tenantId, Long employeeId, LocalDate startDate, LocalDate endDate);
}
```

## 8.2 计算流程

```text
1. 获取员工信息
2. 获取员工适用工作规则
3. 获取当天排班
4. 获取当天打卡记录
5. 打卡记录排序
6. 出勤/退勤配对
7. 休息时间配对
8. 判断缺卡
9. 判断迟到/早退
10. 计算实际工作时间
11. 计算普通工时
12. 计算残业时间
13. 计算深夜劳动时间
14. 计算休日出勤时间
15. 生成异常记录
16. 保存日次勤怠
```

---

# 8.3 打卡配对规则

## 8.3.1 基本规则

```text
当天最早的 CLOCK_IN 作为实际出勤
当天最晚的 CLOCK_OUT 作为实际退勤
BREAK_START 与 BREAK_END 成对计算休息
如果缺少 CLOCK_IN，生成缺出勤卡异常
如果缺少 CLOCK_OUT，生成缺退勤卡异常
```

## 8.3.2 跨日班次

夜班示例：

```text
排班日期：2026-05-24
班次：22:00 - 翌日 07:00
打卡窗口：2026-05-24 18:00 到 2026-05-25 12:00
```

查询打卡时不能只查自然日，要根据排班时间扩大窗口。

## 8.3.3 无排班打卡

```text
如果员工无排班但有打卡：
    生成 NO_SCHEDULE_PUNCH 异常
    仍然计算实际工时
    等待管理员确认是否为临时出勤或误打卡
```

## 8.3.4 有排班无打卡

```text
如果员工有工作排班但没有任何打卡：
    生成 SCHEDULE_NO_PUNCH 异常
    状态为 NO_PUNCH 或 ABSENCE
```

---

# 8.4 迟到计算

```text
如果 actual_clock_in > scheduled_start_time + grace_minutes
    late_minutes = actual_clock_in - scheduled_start_time
否则
    late_minutes = 0
```

建议配置：

```text
grace_minutes = 0 或 5
```

---

# 8.5 早退计算

```text
如果 actual_clock_out < scheduled_end_time
    early_leave_minutes = scheduled_end_time - actual_clock_out
否则
    early_leave_minutes = 0
```

---

# 8.6 实际工时计算

```text
actual_work_minutes = actual_clock_out - actual_clock_in - actual_break_minutes
```

如果没有退勤卡，则不计算完整实际工时，生成异常。

---

# 8.7 休息时间计算

## 8.7.1 打卡休息

如果有休息打卡：

```text
BREAK_START - BREAK_END 成对计算
```

## 8.7.2 自动休息

如果没有休息打卡，可根据规则自动扣休息：

```text
工作超过 6 小时，自动扣 45 分钟
工作超过 8 小时，自动扣 60 分钟
```

该规则需要做成配置，不要写死。

---

# 8.8 残业计算

## 8.8.1 所定外残业

```text
所定外残业 = 实际工时 - 排班工时
```

## 8.8.2 法定外残业

```text
法定外残业 = 实际工时 - 8小时
```

实际系统中要根据员工适用的劳动时间制度调整。

---

# 8.9 深夜劳动计算

深夜时间段默认：

```text
22:00 - 翌日 05:00
```

计算方法：

```text
深夜劳动时间 = 实际工作时间段与深夜时间段的交集 - 深夜期间休息时间
```

---

# 8.10 休日劳动计算

```text
如果 work_day_type = LEGAL_HOLIDAY 或 COMPANY_HOLIDAY
    holiday_work_minutes = actual_work_minutes
```

法定休日和所定休日需要区分，工资计算倍率可能不同。

## 14. 关键业务规则

---

# 14.1 原始数据不可删除原则

```text
punch_raw_log 是事实记录
禁止物理删除
如果误导入，只能标记为 IGNORED
如果需要修正，新增审批或修正记录
```

---

# 14.2 勤怠结果可重算原则

```text
attendance_daily 是计算结果
可以根据排班、打卡、审批重新计算
每次计算需要记录 calculated_at
必要时记录 attendance_calc_log
```

---

# 14.3 月结锁定原则

```text
月结前允许修正
月结后禁止普通用户修改
管理员可解锁
解锁和重新锁定必须记录日志
```

---

# 14.4 外部系统接入原则

```text
不同外部系统的数据格式不同
统一转换成 PunchRawEventDTO
保存原始 raw_payload
通过 source_event_id 防重复
如果没有 source_event_id，则用 source_system + external_employee_id + punch_time + punch_type 生成 hash
```

```text

9. 前端页面先保证业务闭环，不追求过度复杂

11. 技术选型必须贴合 SELATTENDANCE 当前模板基线，不新增超出本设计边界的外部依赖
12. 数据库第一版只使用 H2，schema.sql 和 data.sql 必须可重建最小数据
13. 中日双语是一等需求，页面文案必须从字典读取并支持一键切换
```

# 26. 极限用户友好设计总原则

> 目标：让第一次打开系统的人，不用看说明，也能知道下一步该做什么。  
> 核心标准：界面不是“功能堆叠”，而是“引导用户完成业务”。

本系统前端设计必须遵守以下原则：

```text
1. 页面一打开，就知道当前页面是做什么的
2. 每个页面只突出一个主任务
3. 新用户没有数据时，必须显示下一步引导，而不是空白表格
4. 所有复杂操作必须做成向导式流程
5. 所有关键按钮必须放在用户视线最自然的位置
6. 所有错误必须告诉用户“为什么错、怎么改、点哪里处理”
7. 所有下拉框为空时，必须提示去哪里配置
8. 所有保存、删除、月结、重算等高风险操作必须有确认与回退说明
9. 所有列表必须有清晰筛选、状态标签、批量操作
10. 系统必须默认给出推荐动作，而不是让用户自己猜
```

---

## 26.1 极限友好的产品定位

本系统不是给程序员用的后台，而是给以下用户使用：

```text
1. 学校/企业管理员
2. 店长/教室负责人
3. 排班负责人
4. 工资担当
5. 普通员工
6. 不太懂电脑的兼职员工
```

因此前端文案必须尽量使用业务语言，而不是技术语言。

错误示例：

```text
source_event_id duplicate
employee mapping not found
shift_template_id cannot be null
```

正确示例：

```text
这条打卡记录已经导入过了，系统已自动跳过。
没有找到这个外部员工ID对应的员工，请先绑定员工。
请先选择一个班次，再保存排班。
```

## 26.2 页面设计的统一结构

所有后台页面统一采用以下布局：

```text
顶部区域：页面标题 + 当前任务说明 + 主操作按钮
筛选区域：常用筛选项，默认收起高级筛选
主体区域：表格 / 日历 / 卡片
右侧区域：详情抽屉 / 操作提示 / 异常说明
底部区域：分页 / 批量操作 / 保存状态
```

页面顶部必须有一句“人能看懂的话”：

```text
员工管理：在这里维护员工资料，并绑定外部打卡系统的员工ID。
排班管理：在这里给员工安排每天的班次，可以复制上周排班。
打卡记录：这里显示所有原始打卡数据，异常数据需要处理。
日次勤怠：系统根据排班和打卡自动计算每天的出勤结果。
```

# 41. 补充结论

本系统要做成“用户不用看说明也会操作”的关键，不是增加更多按钮，而是把复杂流程拆成清楚的步骤：

```text
先告诉用户当前页面做什么
再告诉用户下一步做什么
再让用户预览影响
最后让用户确认执行
```

前端体验优先级应高于功能堆叠。

第一版系统最重要的是让用户顺利完成：

```text
添加员工 → 创建班次 → 排班 → 打卡 → 查看日次勤怠 → 处理异常 → 月次汇总 → 导出工资
```

只要这条主线足够顺畅，系统就具备真正可用价值。
