# 月次头部布局抽取为公共模块方案

> 版本：v1.0  
> 适用工程：SELATTENDANCE / SELSP / SELVUE  
> 文档定位：评估当前“标题说明 + 统计卡 + 筛选区”头部布局是否适合抽成 shared 公共模块，并给出可执行的抽取边界、接口设计、迁移顺序与风险控制方案。  
> 目标：避免继续在各业务模块里重复写同类头部结构，同时避免做出一个过重、过死、难维护的万能头部组件。

---

## 0. 结论先说

可以抽，但**不建议把月次头部原样直接抽成一个写死业务的公共组件**。

更合适的做法是：

- 抽一个共享“头部布局壳组件”
- 标题说明、统计卡、筛选区、操作区都通过 `props + slots` 传入
- 先在 `attendance` 项目内验证
- 验证稳定后再决定是否向 `SELTEMPLATE` 或更高层共享

一句话结论：

- **值得抽**
- **应抽壳，不应抽死内容**
- **优先做 shared 布局组件，不要做万能业务组件**

---

## 1. 当前现状

### 1.1 月次头部当前结构

当前月次头部已经在 `AttendanceWorkbenchView.vue` 页面层形成了相对完整的独立布局，包含：

- 左侧标题说明
  - `月次汇总`
  - `先把已锁定的日次结果按月聚合，再确认能否月结、反结和导出。`
- 右侧统计卡
  - 待汇总
  - 可月结
  - 已月结
  - 已反结
- 下方筛选区
  - 所属月份
  - 事业所
  - 部门名称
  - 员工姓名
  - 搜索按钮
  - 月结状态
  - 只看仍有阻塞的月次

### 1.2 其他模块已有相似结构

当前至少有以下模块已经反复使用了“标题说明 + 统计卡 + 筛选区/工具栏”的模式：

- 打卡记录 `PunchSection.vue`
- 日次结果 `DailySection.vue`
- 异常处理 `CaseSection.vue`

这些模块虽然位置还在各自列表面板内，但结构模式高度相似：

- 标题说明
- 统计卡
- 筛选区
- 刷新/操作按钮

这说明当前不是单个页面偶发重复，而是已经形成一类稳定 UI 家族。

---

## 2. 为什么值得抽

### 2.1 重复结构已经足够明显

当前项目已经重复维护这些能力：

- 标题区间距
- 标题和说明的排版
- 统计卡网格
- 统计卡不同色块风格
- 筛选栏网格
- 筛选栏响应式断点
- 搜索按钮、复选框、下拉框对齐

如果继续按页面各写一份，后续会出现这些问题：

- 同类模块视觉不一致
- 每次改一个头部布局都要改多处
- 响应式断点重复维护
- 新模块加入时继续复制旧结构

### 2.2 当前 shared 层已经证明这类抽取方式可行

目前项目已经有以下共享组件：

- `ThreePaneWorkbenchLayout`
- `SharedDataTable`
- `SharedPaginationBar`

这说明项目本身已经接受这种模式：

- shared 负责壳层与布局能力
- 业务页负责具体内容和数据

因此，头部布局也适合沿用同一路线。

---

## 3. 为什么不能直接做“万能头部组件”

如果直接把月次头部整块写成一个所谓万能组件，会很快出现失控：

- 月次是左文案右统计卡
- 打卡/日次/异常处理当前是列表面板内头部
- 不同模块统计卡数量不同
- 操作按钮数量不同
- 筛选项数量不同
- 有的模块需要搜索按钮
- 有的模块不需要
- 有的模块需要复选框
- 有的模块没有

如果全部硬塞进一个组件，最后大概率会变成：

- prop 数量很多
- 分支判断很多
- 默认样式很多
- 插槽和配置混杂
- 可读性和维护性快速下降

所以不建议做：

- `UniversalBusinessHeader.vue`

建议做：

- `SharedWorkbenchHeader.vue`
- `SharedMetricCards.vue`

也就是拆成“布局壳 + 子能力”，不是做一个业务万能组件。

## 4. 推荐抽取方案

### 4.1 推荐组件边界

建议抽两层：

#### 方案 A：先抽一个总壳组件

组件名建议：

- `src/shared/components/SharedWorkbenchHeader.vue`

职责：

- 统一头部外层容器
- 统一标题说明区布局
- 统一统计卡区布局
- 统一筛选区容器布局
- 统一响应式断点

不负责：

- 具体统计卡内容
- 具体筛选字段
- 月次、打卡、日次、异常处理的业务文案
- 查询逻辑、按钮事件

#### 方案 B：再补一个统计卡子组件

组件名建议：

- `src/shared/components/SharedMetricCards.vue`

职责：

- 按配置渲染统计卡
- 支持 2/4/5 张卡
- 支持卡片 tone
  - default
  - warm
  - danger
  - muted

不负责：

- 筛选区
- 标题说明
- 业务接口数据获取

### 4.2 推荐接口草案

#### `SharedWorkbenchHeader.vue`

建议最小接口：

```vue
<SharedWorkbenchHeader
  :title="..."
  :lead="..."
  :split-mode="'stacked' | 'left-summary-right-metrics'"
  :header-class-name="..."
>
  <template #metrics>
    <!-- 统计卡 -->
  </template>

  <template #filters>
    <!-- 筛选区 -->
  </template>

  <template #actions>
    <!-- 可选动作区 -->
  </template>
</SharedWorkbenchHeader>
```

说明：

- `title`
  - 标题
- `lead`
  - 说明文案
- `split-mode`
  - 控制标题说明和统计卡是上下堆叠，还是左右布局
- `metrics`
  - 放统计卡
- `filters`
  - 放筛选区
- `actions`
  - 放独立操作区

### 4.3 动作边界规则

这一条需要作为后续接入 shared 头部时的固定规则：

- `头部动作`
  - 只放全页概览层动作
  - 例如：影响整页状态理解的总览级切换、全局导出入口、跨列表的全局开关
- `列表区动作`
  - 放在 `SharedDataTable` 上方或列表面板顶部
  - 例如：刷新列表、按当前筛选重算、批量处理、批量提交、批量导出当前列表
- `详情区动作`
  - 放在右侧详情、审批区、表单区内部
  - 例如：单条重算、审批通过、退回、驳回、锁定、解锁、编辑当前记录

### 4.4 为什么不能把列表动作继续塞进头部

如果把列表区动作默认放进 `SharedWorkbenchHeader` 的 `actions` 槽，会持续出现下面的问题：

- 头部越来越像万能工具栏，失去“概览层”边界
- 列表动作和表格结果分离，用户需要上下跳着看
- 同家族页面会反复出现边界不一致
  - 有的刷新按钮在头部
  - 有的刷新按钮在表格区
- shared 头部会越来越重，最后变成写死业务的万能组件

因此建议把 `actions` 槽保留为能力，但只在“真正的头部概览动作”场景下使用，不再默认承接每个列表页的刷新和批量动作。

#### `SharedMetricCards.vue`

建议接口：

```vue
<SharedMetricCards :items="metricItems" />
```

其中 `metricItems` 结构建议：

```js
[
  { value: 1, label: '待汇总', tone: 'default' },
  { value: 0, label: '可月结', tone: 'warm' },
  { value: 0, label: '已月结', tone: 'default' },
  { value: 0, label: '已反结', tone: 'muted' }
]
```

## 5. 哪些模块适合先接入

### 第一批最适合

- `monthly`
- `punch`
- `daily`
- `case`

原因：

- 都有标题说明
- 都有统计卡
- 都有筛选区
- 结构足够像
- 都属于“工作台数据模块”

### 第二批再评估

- `schedule`

原因：

- 虽然也有工具栏，但它核心是排班看板
- 布局和交互重心不同
- 不应为了统一而强行靠拢

### 当前不建议接入

- `workplace`
- `department`
- `employee`
- `shift`

原因：

- 这些更偏基础资料管理页
- 主要是表单 + 列表
- 不是“指标型工作台头部”家族

---

## 6. 推荐迁移顺序

### 第一步

先只抽 `SharedMetricCards.vue`

原因：

- 风险最低
- 当前 `punch / daily / case / monthly` 都能立即受益
- 统计卡结构最稳定

### 第二步

再抽 `SharedWorkbenchHeader.vue`

原因：

- 月次现在最适合作为首个完整接入样板
- 因为它已经是页面层头部，不在 section 内部缠绕太深

### 第三步

把 `punch / daily / case` 接到新头部壳

接法建议：

- 先保持业务逻辑完全不动
- 只替换模板外壳
- 统计卡与筛选区继续走现有字段

## 7. 实施建议

### 7.1 第一阶段只做 attendance 内部 shared

先放在：

- `SELATTENDANCE/SELVUE/src/shared/components`

不要第一步就抽到：

- `SELTEMPLATE`
- 更高层公共仓

原因：

- 当前样式和命名带有明显 attendance 语义
- 需要先证明这套接口能同时承住 monthly / punch / daily / case

### 7.2 样式也要一起收口

当前与头部相关的样式分散在：

- `selattendance-punch-summary`
- `selattendance-punch-summary-card`
- `selattendance-schedule-toolbar`
- `selattendance-monthly-header-*`

建议：

- 抽组件时同步搬迁共性样式到 shared 组件内部
- 页面级只保留真正业务特有样式

### 7.3 不要把筛选逻辑抽进 shared

shared 只负责：

- 容器布局
- 样式
- 插槽边界

业务页继续负责：

- `v-model`
- 查询参数
- 点击事件
- 是否自动查询
- 后端接口调用

---

## 8. 风险点

### 风险 1：做成 props 过多的万能组件

后果：

- 难维护
- 难理解
- 后面每接一个模块都加分支

规避办法：

- 多用插槽
- 少堆业务 props

### 风险 2：抽得太早，把 attendance 私有样式带到更高层

后果：

- shared 被 attendance 绑死
- 其他项目难用

规避办法：

- 第一阶段只在 attendance 自己的 shared 内验证

### 风险 3：把筛选行为和 UI 壳混在一起

后果：

- shared 组件变成业务组件
- 不同页面逻辑冲突

规避办法：

- shared 不持有业务状态
- 业务逻辑全部留在页面或 composable

---

## 9. 最终建议

最终建议是：

1. 值得抽。
2. 先抽 `SharedMetricCards.vue`。
3. 再抽 `SharedWorkbenchHeader.vue`。
4. 先在 `monthly` 做完整样板。
5. 再迁 `punch / daily / case`。
6. 不要做一个写死业务的万能头部组件。

最稳妥的落地策略是：

- **抽布局壳**
- **抽统计卡**
- **保留业务逻辑在原模块**

这样既能减少重复，又不会把共享层做坏。

---

## 10. 建议下一步

如果要进入实施，建议下一轮直接做下面这件事：

- 新建 `SharedMetricCards.vue`
- 新建 `SharedWorkbenchHeader.vue`
- 先把 `monthly` 接成第一版样板
- 保持 `punch / daily / case` 先不动
- 样板验证通过后，再决定是否批量迁移

这会是风险最低、收益最高的路径。
