# 第八阶段：外部打卡系统正式接入详细设计文档

> 版本：v1.0  
> 目标阶段：阶段 8  
> 适用工程：SELATTENDANCE / SELSP / SELVUE  
> 文档定位：在第七阶段已经形成稳定规则层之后，正式接入外部打卡系统配置、Webhook / Pull 数据接收、员工 ID 映射、同步日志与失败重试能力。  
> 设计原则：继续沿用当前考勤工作台风格、中日双语、一键启动、用户极度友好；普通管理员不需要理解第三方 API 细节，也能完成接入配置、测试连接、错误定位和重处理。

---

## 0. 当前实现问题与优先修正项

### 0.1 当前实现现状

当前已经完成或基本完成：

- 第一阶段基础资料与初始化向导。
- 第二阶段排班管理闭环。
- 第三阶段打卡接收与原始数据管理：
  - `CUSTOM_WEBHOOK` 与 `CSV_IMPORT` 基础入口
  - 原始打卡落库
  - 手动补录
  - 绑定 / 忽略 / 重处理
- 第四阶段日次勤怠计算与异常处理。
- 第五阶段异常处理与审批闭环。
- 第六阶段月次汇总、月结、反结与导出。
- 第七阶段日本规则增强：
  - 正式规则配置
  - 员工适用关系
  - 深夜 / 休日 / 残业增强结果
  - 规则预警看板

当前已经具备的外部接入基础：

- `punch_raw_log` 已能承接原始打卡数据。
- 工作台已具备独立区块、共享头部、详情侧栏和操作提示体系。
- 打卡处理链已具备“接入后继续进入原始打卡 -> 日次 -> 月次 -> 规则增强”的主链路。
- 当前系统已有导入日志、异常提示和重处理入口的交互基础。

当前尚未正式实现：

- 多外部打卡系统正式接入页。
- 接入配置主表和加密保存策略。
- 第三方 API Key / Secret / Webhook Secret 的正式管理界面。
- 测试连接。
- 员工外部 ID 映射管理。
- Webhook 签名校验。
- API Pull 定时任务。
- 同步日志与失败重试页。
- 连接器抽象层的正式扩展点。

### 0.2 当前核心问题

问题 1：当前系统能处理“已经进来的打卡”，但还不能稳定管理“打卡是怎么进来的”。

现在可以做：

- CSV 导入
- 自定义 Webhook 接收
- 手动补录

但还不能正式告诉管理员：

- 第三方平台到底接通没有
- 员工外部 ID 是否都已匹配
- 哪条同步失败了
- 为什么失败
- 能否一键重试

问题 2：第三方接入配置还没有统一模型。

如果没有正式配置主表和接入向导：

- API Key 会散在代码或临时配置里
- Webhook Secret 无法规范保存
- 多平台接入会互相覆盖
- 后续租户化时很难做隔离

问题 3：外部接入如果直接把数据写进后续结果层，会破坏前面七个阶段的边界。

第八阶段必须明确：

- 外部系统只负责“把原始打卡带进来”
- 规则解释仍由第七阶段规则层承担
- 日次和月次口径不能被第三方平台直接覆盖

否则会出现：

- 外部平台算一套
- 本系统又算一套
- 用户不知道哪套才是最终结果

问题 4：普通管理员不应该被第三方平台技术字段淹没。

如果页面直接暴露：

- 请求签名算法
- Header 名
- 回调字段映射 DSL
- OAuth 细节

管理员就很难完成接入。

第一版必须尽量把复杂性压到：

- 连接器层
- 接入配置模型
- 同步日志解释层

### 0.3 当前字段 / 结构是否可以复用

可以复用：

- 第三阶段已有 `punch_raw_log` 原始打卡结构。
- 员工主数据、部门、事业所可继续承接外部员工映射。
- 打卡工作台、日志表格、详情抽屉、统一确认框可以继续复用。
- 第四阶段日次服务和第七阶段规则层可以继续承接外部接入后的后续计算。

仍然不足：

- 现有原始打卡结构只解决“数据进来以后怎么处理”，没有正式表达“接入系统是谁、配置是什么、同步状态如何”。
- 现有员工主数据没有正式外部 ID 映射管理页。
- 现有日志还没有形成“同步日志 + 失败原因 + 重试动作”的正式模型。
- 现有第三阶段入口偏单体处理，还没有多连接器统一接口。

### 0.4 开发前必须先修正的事项

1. 必须先确认第七阶段规则层已经稳定，不允许第八阶段外部接入绕过规则增强链。
2. 必须先定义第八阶段只做“外部接入”，不提前混入第九阶段租户权限与运营增强。
3. 必须明确第一版先做哪些连接器：
   - `CUSTOM_WEBHOOK` 正式化
   - `CSV_IMPORT` 继续保留
   - 第三方商用平台连接器先预留扩展位，不要求全部第一版实现
4. 必须明确哪些密钥需要加密保存、哪些仅做掩码回显。
5. 必须明确接入失败后的最小补救链路：
   - 查看日志
   - 看具体原因
   - 修映射或修配置
   - 重试

## 1. 阶段目标

第八阶段目标是把当前“能处理内部打卡数据”的系统，增强为“能正式接入外部打卡系统并稳定导入原始打卡”的系统。

本阶段完成后，用户应该可以：

- 新增一个外部打卡系统接入配置。
- 测试连接是否正常。
- 查看系统生成的 Webhook URL。
- 复制接入地址给第三方平台。
- 管理员工外部 ID 映射。
- 查看最近同步结果。
- 看见失败原因。
- 重试失败同步。
- 让接入后的打卡继续进入第三阶段、第四阶段、第七阶段既有链路。

本阶段不做：

- 直接使用第三方平台的工时结果替代本系统结果。
- 绕过第七阶段规则层直接生成月次预警。
- 多租户隔离控制台。
- 平台级权限中心。
- 社保、税务、薪资平台联动。

这些能力进入第九阶段及后续专题阶段。

## 3. 核心设计原则

### 3.1 原则 1：外部接入只负责把原始打卡带进来

外部系统接入层不直接产出：

- 最终日次结论
- 月次结论
- 规则预警结论

这些仍由：

- 第三阶段原始打卡处理
- 第四阶段日次计算
- 第六阶段月次聚合
- 第七阶段规则增强

继续负责。

### 3.2 原则 2：连接器差异下沉到后端，页面统一成人话

不同平台的差异应该主要放在：

- Connector 实现
- 签名校验
- 字段映射
- Pull 参数

页面层尽量统一成：

- 接入名称
- 接入方式
- 测试连接
- 最近同步
- 失败原因

### 3.3 原则 3：先给最小闭环，再逐步扩平台

第一版建议先做：

- `CUSTOM_WEBHOOK` 正式化
- `CSV_IMPORT` 继续保留
- Pull 结构预留
- 商用平台 Connector 扩展点预留

而不是一次性做完所有第三方平台。

### 3.4 原则 4：失败必须可看、可解释、可重试

管理员最怕的是：

- 不知道接没接通
- 失败后只看到“失败”
- 无法知道是哪条数据失败
- 无法重试

所以第八阶段必须强制提供：

- 测试连接结果
- 同步日志
- 失败原因
- 重试入口

## 4. 方案设计

### 4.1 总体方案

第八阶段拆成五块：

1. 接入配置管理  
2. 员工外部 ID 映射  
3. Webhook / Pull 接入处理  
4. 同步日志与失败重试  
5. 与第三阶段原始打卡层衔接

总体链路如下：

```text
管理员配置接入
-> 测试连接
-> 配置员工外部 ID 映射
-> 第三方推送或系统定时拉取
-> 连接器标准化第三方数据
-> 写入同步日志
-> 员工匹配
-> 写入 punch_raw_log
-> 继续进入第三阶段既有处理
-> 后续进入第四 / 六 / 七阶段
```

### 4.2 连接器标准接口

建议定义统一的 `PunchConnector` 抽象接口：

| 方法 | 说明 |
| --- | --- |
| `testConnection()` | 测试当前配置是否可用 |
| `pullPunches()` | 主动拉取原始打卡 |
| `parseWebhook()` | 解析 Webhook 请求 |
| `verifyWebhookSignature()` | 校验签名 |
| `normalizePunchRecords()` | 转成系统统一原始打卡结构 |

第一版至少正式实现：

- `CustomWebhookConnector`

第一版可预留：

- `KingOfTimeConnector`
- `TouchOnTimeConnector`
- `JobcanConnector`

### 4.3 数据标准化方案

所有第三方数据进入系统前，统一标准化为：

| 字段 | 说明 |
| --- | --- |
| connectorId | 来自哪套接入 |
| externalRequestId | 第三方请求或批次标识 |
| externalEmployeeId | 第三方员工标识 |
| punchTime | 打卡时间 |
| punchType | 上班 / 下班 / 休息开始 / 休息结束 |
| sourcePayload | 原始负载快照 |
| normalizedPayload | 标准化后的结构 |

标准化后再写入第三阶段原始打卡主结构。

### 4.4 员工映射方案

员工映射第一版不建议做复杂智能匹配。

建议顺序：

1. 先按 `externalEmployeeId` 精确匹配  
2. 再按 `externalEmployeeCode` 辅助匹配  
3. 未命中时进入“待处理映射”列表  
4. 管理员手工绑定后允许重试

### 4.5 同步日志与失败重试方案

同步日志至少记录：

- 接入主键
- 接入名称
- 触发方式
- 请求时间
- 处理结果
- 成功条数
- 失败条数
- 失败原因
- 是否已重试
- 最近重试时间

失败重试第一版只要求：

- 重试单次同步批次
- 重试后重新走标准化、匹配和落库链

### 5.3 配置项设计

第一版建议可配置项：

- Webhook 是否启用
- Pull 是否启用
- Pull 周期
- 默认归属事业所
- 未映射员工是否直接拒绝入库
- 同步失败是否允许手工重试

默认值建议：

- `activeFlag=true`
- `receiveMode=WEBHOOK`
- `retryFlag=false`
- Pull 默认关闭，避免系统一接通就自动跑批

## 6. 关键流程设计

### 6.1 新增接入配置

```text
管理员打开外部接入页
-> 新增接入
-> 选择平台类型
-> 填接入名称和方式
-> 填 API / Secret / Webhook Secret
-> 保存
-> 生成可复制的接入说明
```

### 6.2 测试连接

```text
管理员点击测试连接
-> 后端按 connector 类型调用 testConnection
-> 返回 成功 / 失败
-> 页面显示具体结果
```

### 6.3 Webhook 接收

```text
第三方系统推送 webhook
-> 校验签名
-> 记录同步日志
-> 解析第三方 payload
-> 标准化打卡数据
-> 映射内部员工
-> 写入 punch_raw_log
-> 返回处理结果
```

### 6.4 Pull 任务

```text
定时任务触发
-> 读取启用中的 pull 接入配置
-> 调用对应 connector 拉取数据
-> 写同步日志
-> 标准化
-> 员工映射
-> 写入 punch_raw_log
```

### 6.5 失败重试

```text
管理员打开同步日志
-> 查看失败记录
-> 修正映射或配置
-> 点击重试
-> 重新走标准化和落库链
-> 更新日志结果
```

## 7. 页面设计

### 7.1 工作台区块建议

建议新增一个独立区块：

- `connector`

页面仍沿用当前 workbench 模式：

- 左栏：接入配置列表
- 中栏：接入配置表单 / 测试连接 / 复制接入地址
- 右栏：员工映射 / 同步日志 / 失败详情

### 7.2 页面重点

必须有：

- 接入名称
- 平台类型
- 接收方式
- 启用状态
- 测试连接
- 复制 Webhook URL
- 员工映射列表
- 最近同步记录
- 失败原因展示
- 重试按钮

### 7.3 用户友好要求

- 不直接展示复杂签名算法名给普通管理员。
- 失败提示优先用人话，例如：
  - 员工未匹配
  - API Key 无效
  - Webhook 签名不通过
  - 第三方接口超时
- 对敏感字段统一掩码显示。
- 默认先给 `Custom Webhook` 说明示例。

### 8.3 与现有阶段的衔接改动点

- 第三阶段原始打卡入口要支持来自 connector 的标准化数据。
- 第四阶段、第五阶段、第六阶段、第七阶段不改主边界，只继续消费原始打卡链输出。
- 第七阶段规则层必须明确保留在第八阶段之后仍为正式解释层。

---

## 9. 风险点

风险 1：第三方平台字段结构差异过大，第一版如果没有标准化层，很快会把第三阶段原始打卡结构污染。

风险 2：如果员工外部 ID 映射做得太弱，接入成功后会堆积大量“无法归属员工”的打卡。

风险 3：如果同步日志只记成功失败，不记原因，管理员无法定位问题。

风险 4：如果第八阶段让第三方结果直接覆盖规则层，会破坏第七阶段的正式口径。

风险 5：如果敏感配置不加密保存，后续进入第九阶段会留下较大安全隐患。

---

## 10. 验证方案

### 10.1 后端验证

- 可以新增接入配置
- 可以测试连接
- 可以接收合法 Webhook
- 非法签名会被拒绝
- 可以写同步日志
- 员工未匹配时能产出明确失败原因
- 可以重试失败批次

### 10.2 前端验证

- 外部接入区块可正常显示
- 接入配置可保存
- 测试连接有明确成功 / 失败提示
- Webhook URL 可复制
- 员工映射可新增 / 编辑
- 同步日志能看见失败原因
- 重试按钮可见且可操作

### 10.3 联动验证

- 第三方打卡进入后能写入 `punch_raw_log`
- 后续仍能进入第四阶段日次计算
- 第七阶段规则增强结果不会被绕过

### 10.4 验收标准

- 可以新增外部打卡系统配置
- 可以测试连接
- 可以完成员工外部 ID 映射
- 可以接收第三方 Webhook 或拉取数据
- 可以查看同步日志
- 可以重试失败数据
- 接入后的打卡仍进入现有勤怠主链路

---

## 11. 与第九阶段的衔接

第九阶段如果进入 SaaS 化与权限运营增强：

- 第八阶段的接入配置要纳入租户隔离
- 敏感配置读取要接入权限控制
- 同步日志要纳入操作审计

但第八阶段本身不提前实现：

- 平台级租户接入管理
- 统一权限中心
- 多租户级运营后台

---
