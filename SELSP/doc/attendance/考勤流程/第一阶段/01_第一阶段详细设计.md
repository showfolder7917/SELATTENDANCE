### 0.4 开发前必须先修正的事项

2. 必须明确第一阶段的“公司/教室设置”由 `tenant` 负责，避免后续和 SaaS 多租户阶段混淆。
3. 必须明确第一阶段的“勤怠规则”只做默认配置占位，不实现复杂残业、深夜、休日等高级规则。
4. 必须明确第一阶段所有页面都要满足双语与空状态引导要求，不能先做纯 CRUD 再补体验。

## 1. 目标

第一阶段的目标不是完成考勤计算，而是完成系统启用前的基础资料准备闭环，让管理员可以顺利把系统从“空系统”推进到“可进入排班阶段”的状态。

第一阶段完成后，用户应当能够：

- 设置公司 / 教室基础信息。
- 新增事业所。
- 新增部门。
- 新增员工并维护基础信息。
- 维护员工外部打卡系统绑定关系。
- 创建班次模板。
- 一键生成推荐班次模板。
- 在初始化向导中看到当前准备进度和下一步建议。

## 2. 输入与输出边界

### 2.1 输入

第一阶段主要输入来源如下：

- 管理员手工录入的公司 / 教室信息。
- 管理员手工录入的事业所信息。
- 管理员手工录入的部门信息。
- 管理员手工录入或批量导入的员工信息。
- 管理员手工录入的外部打卡系统绑定信息。
- 管理员手工录入或一键生成的班次模板。
- 前端本地语言设置 `zh-CN / ja-JP`。

第一阶段主输入字段包括：

- 租户基础信息：
  - 租户编码
  - 租户名称
  - 联系人
  - 联系方式
  - 时区
- 事业所基础信息：
  - 事业所编码
  - 事业所名称
  - 地址
  - 电话
- 部门基础信息：
  - 所属事业所
  - 父部门
  - 部门编码
  - 部门名称
  - 排序号
- 员工基础信息：
  - 员工编号
  - 员工姓名
  - 员工假名
  - 性别
  - 雇佣类型
  - 入社日
  - 退社日
  - 邮箱
  - 电话
  - 所属事业所
  - 所属部门
- 外部打卡映射：
  - 外部系统名称
  - 外部员工 ID
  - 外部员工编号
- 班次模板：
  - 模板编码
  - 模板名称
  - 班次类型
  - 开始时间
  - 结束时间
  - 是否跨日
  - 休息分钟数
  - 颜色

### 2.2 输出

第一阶段输出对象如下：

- 已落库的基础资料数据。
- 可供后续排班阶段直接使用的员工与班次模板基础主数据。
- 初始化向导进度状态。
- 员工导入与导出结果。
- 推荐班次模板生成结果。

第一阶段输出限制如下：

- 不输出排班结果。
- 不输出打卡原始记录。
- 不输出日次勤怠计算结果。
- 不输出月次汇总结果。
- 不输出审批流程结果。

## 3. 核心设计原则

- 原则 1：第一阶段只做“系统启用前准备”，不抢做后续阶段业务闭环。
- 原则 2：优先保证基础主数据完整、可维护、可双语展示。
- 原则 3：页面必须极限友好，不能让管理员面对空表格和无下一步提示。
- 原则 4：班次时间优先通过模板选择，不要求用户手动反复输入复杂时间。
- 原则 5：员工与外部打卡系统的映射必须在第一阶段预留完成，避免第三阶段接打卡时再回补基础数据。
- 原则 6：所有状态、按钮、表头、提示文案都必须支持中日双语切换。

## 4. 方案设计

### 4.1 第一阶段总体方案

第一阶段按“初始化向导驱动基础资料完善”的模式落地。

主流程如下：

```text
进入系统
  ↓
发现基础资料未完成
  ↓
进入初始化向导
  ↓
设置公司/教室
  ↓
新增事业所
  ↓
新增部门
  ↓
新增员工或批量导入员工
  ↓
绑定外部打卡 ID
  ↓
创建班次模板或一键生成推荐班次
  ↓
显示第一阶段完成，可进入排班阶段
```

### 4.2 初始化向导设计

初始化向导沿用原始文档中的步骤，但按第一阶段正式收敛为以下 7 步：

```text
第 1 步：设置公司/教室信息
第 2 步：添加事业所
第 3 步：添加员工
第 4 步：创建班次模板
第 5 步：配置勤怠规则（第一阶段仅默认规则占位）
第 6 步：开始排班（提示未开放，作为下一阶段入口）
第 7 步：导入或接收打卡（提示未开放，作为第三阶段入口）
```

第一阶段真正需要完成的步骤是前 1 到 5 步，其中第 5 步只做默认规则确认，不做复杂规则配置。

每一步必须支持以下状态：

```text
未开始
进行中
已完成
需要处理
```

页面必须显示：

- 当前完成进度。
- 未完成项。
- 推荐下一步。
- 直接操作按钮。

### 4.3 员工管理设计

员工管理页面必须满足以下布局：

- 顶部：
  - 页面标题
  - 页面说明
  - 新增员工按钮
  - 批量导入按钮
- 筛选区：
  - 姓名
  - 员工编号
  - 部门
  - 雇佣类型
  - 状态
- 主体表格：
  - 员工编号
  - 姓名
  - 部门
  - 事业所
  - 雇佣类型
  - 入社日
  - 外部打卡 ID
  - 状态
  - 操作
- 右侧抽屉：
  - 员工详情
  - 编辑员工
  - 绑定外部打卡 ID

必须提供三种新增方式：

- 单个新增
- 批量导入
- 从外部打卡系统同步（第一阶段可先留入口）

### 4.4 事业所与部门管理设计

事业所和部门是员工归属的基础主数据，第一阶段必须先行建设。

设计要求：

- 事业所支持基础 CRUD。
- 部门支持基础 CRUD。
- 部门支持父子层级。
- 员工选择部门时，若当前没有部门数据，必须直接提供“去新增”入口。
- 员工选择事业所时，若当前没有事业所数据，必须直接提供“去新增”入口。

### 4.5 班次模板设计

班次模板页面必须支持：

- 模板列表。
- 模板详情编辑。
- 新增模板。
- 停用模板。
- 一键生成推荐模板。

系统默认推荐模板如下：

```text
早班：09:00 - 18:00，休息60分钟
晚班：13:00 - 22:00，休息60分钟
夜班：22:00 - 翌07:00，休息60分钟
半日：09:00 - 13:00，无休息
休息：休み
有休：有給
```

时间友好逻辑：

- 当结束时间早于开始时间时，页面必须提示是否设为跨日班次。
- 不要求管理员手动理解跨日存储规则，页面直接给出“设为跨日班次”按钮。

### 4.6 默认勤怠规则占位设计

虽然完整勤怠规则增强在后续阶段，但初始化向导已经包含“配置勤怠规则”步骤，因此第一阶段需要最小落地：

- 为员工保留 `employee_work_rule` 最小结构。
- 默认标准日工时为 `480` 分钟。
- 默认标准周工时为 `2400` 分钟。
- 默认开启加班、深夜、休日计算开关字段，但不在第一阶段展开复杂计算。
- 页面只允许用户确认默认规则或做非常轻量的修改。

### 4.7 双语与极限友好要求

第一阶段所有页面必须满足：

- 页面标题清楚。
- 页面说明使用人话。
- 没有数据时显示引导卡，不显示空白大表格。
- 没有员工时提示“请先添加员工”。
- 没有班次模板时提示“一键生成推荐班次”。
- 员工没有外部打卡 ID 时显示黄色提醒。
- 下拉没有选项时，提供“去新增”按钮。
- 所有页面文案都可切换中文 / 日语。

### 5.2 可先复用的字段设计

- 员工、部门、事业所、班次模板等字段可直接复用总文档中的定义。
- 第一阶段不需要新增额外复杂业务字段。
- `tenant_id` 必须在第一阶段就进入主表，避免后续多租户化时再回填。

### 5.3 第一阶段字段差距判断

- `employee_work_rule` 在总文档中已定义，可以直接作为“默认勤怠规则占位表”使用。
- 第一阶段无需补充复杂打卡源配置、排班锁定、计算日志等后续字段。
- 第一阶段只需确保：
  - 主数据完整。
  - 可被后续排班与打卡阶段直接引用。

### 5.4 配置项设计

第一阶段建议固定以下默认配置：

- 默认语言：`ja-JP`
- 支持语言：`zh-CN`、`ja-JP`
- 默认时区：`Asia/Tokyo`
- 默认标准日工时：`480`
- 默认标准周工时：`2400`
- 推荐班次生成开关：启用

## 7. 风险点

- 风险 1：如果第一阶段把“勤怠规则”展开过深，会提前侵入第 7 阶段的日本规则增强范围。
- 风险 2：如果第一阶段不落 `employee_external_mapping`，第三阶段接打卡时会缺少员工匹配基础。
- 风险 3：如果页面只做 CRUD 不做引导，会直接违背“极限友好”的核心目标。
- 风险 4：如果第一阶段不从一开始支持双语，后续补国际化会导致页面、枚举、导出标题全面返工。
