# 第三阶段：打卡接收与原始数据管理详细设计文档

> 版本：v1.0  
> 目标阶段：阶段 3  
> 适用工程：SELATTENDANCE / SELSP / SELVUE  
> 文档定位：在阶段 1 基础资料与阶段 2 排班管理之后，补齐“打卡事实数据”的接收、导入、查看和人工处理闭环。  
> 设计原则：保持当前考勤工作台页面风格，中日双语，一键启动，用户不需要看说明也能完成主流程。

---

## 0. 当前实现问题与优先修正项

### 0.1 当前实现现状

当前已经完成或基本完成：

- 基础资料：租户、事业所、部门、员工。
- 员工外部打卡 ID 绑定入口。
- 班次模板。
- 排班管理核心闭环：月视图、单格排班、批量排班、复制上周 / 上月、未排班检查、排班导出。
- 前端工作台：左侧功能导航、中间主操作区、右侧辅助面板、中日双语、主题切换。

当前尚未正式实现：

- `punch` 后端子域。
- `punch_raw_log` 原始打卡记录表。
- `punch_import_batch` 导入批次表。
- `punch_source_config` 打卡来源配置表。
- 手动打卡接口。
- CSV 导入接口。
- Webhook 接收接口。
- 打卡记录查询页面。
- 打卡详情抽屉。
- 未匹配员工处理面板。
- 导入批次结果页。

当前已经存在的铺垫：

- 员工管理中已有外部打卡 ID 绑定字段和入口。
- 初始化向导中已有 `punch` 阶段门禁文案。
- 阶段 2 排班已经能提供后续打卡匹配所需的计划数据。

### 0.2 当前核心问题

问题 1：系统现在只有“排班计划”，还没有“打卡事实”。

阶段 2 已经能安排员工每天应该上什么班，但还没有办法接收员工真实的出勤、退勤、休息开始、休息结束等打卡数据。

问题 2：员工外部 ID 已经能绑定，但还没有被用于自动匹配。

员工资料中已经有外部打卡 ID，但还没有 `punch` 模块读取这份映射，把外部打卡记录自动关联到员工。

问题 3：没有原始数据留痕。

后续日次计算、异常判断、审批修正都必须基于原始打卡数据。如果阶段 3 不保存原始 payload，后续出现导入错误或外部系统字段变化时无法追溯。

问题 4：CSV 导入和 Webhook 接收缺少统一处理模型。

手动打卡、CSV、Webhook、未来 API 拉取都应该进入同一张原始记录表，而不是每种来源各自落库。

问题 5：用户遇到“员工未匹配”时需要直接给出处理路径。

极度友好版不能只显示错误码。页面必须告诉用户这条记录为什么没匹配上，并给出“绑定已有员工 / 创建新员工 / 忽略”三个明确动作。

### 0.3 当前字段 / 结构是否可以复用

可以复用：

- 员工表中的员工主键、员工编号、员工姓名、所属部门、事业所。
- 员工外部打卡 ID 绑定结构。
- 阶段 2 的排班数据，用于阶段 4 计算时做打卡匹配。
- 当前工作台页面结构和右侧详情面板交互模式。
- 当前中日双语字典组织方式。
- 当前 shared 组件中的确认弹窗和浮层提示组件。

仍然不足：

- 员工外部打卡 ID 只能说明“外部 ID 与员工的关系”，不能保存每次打卡事实。
- 排班表只表示计划，不能承担原始打卡记录职责。
- 现有前端没有打卡列表、导入预览、批次结果、原始 JSON 查看能力。
- 现有后端没有 punch 来源、去重、导入批次、处理状态、原始 payload 的统一模型。

### 0.4 开发前必须先修正的事项

1. 确认 `employee_external_mapping` 或现有员工外部 ID 字段的读取口径，作为第三阶段自动匹配员工的唯一入口。
2. 先建立 `punch` 后端子域，再做页面，避免前端先写死 mock 结构。
3. 明确 CSV 第一版模板字段，不要一开始支持所有外部系统格式。
4. Webhook 第一版只做 `CUSTOM` 来源的稳定接收，King Of Time、Touch On Time、Jobcan 放到后续外部系统正式接入阶段。
5. 所有导入和接收都必须保存原始 payload，不允许只保存解析后的字段。

## 1. 阶段目标

第三阶段目标是让系统开始接收真实打卡事实数据，并让管理员能清楚处理导入、未匹配、重复和错误记录。

本阶段完成后，用户应该可以：

- 手动创建一条员工打卡记录。
- 下载 CSV 模板。
- 导入 CSV 打卡文件。
- 在导入前预览前 10 行。
- 在导入后看到成功、失败、重复、未匹配数量。
- 通过 Webhook 接收一条外部打卡记录。
- 查看所有原始打卡记录。
- 打开右侧详情查看原始 JSON 和处理日志。
- 对员工未匹配记录执行绑定已有员工、创建新员工、忽略。
- 对失败记录执行重新处理。
- 对误导入记录执行忽略。

本阶段不做：

- 日次勤怠计算。
- 月次勤怠汇总。
- 迟到早退判断。
- 审批补卡。
- 有休申请。
- 工资导出。
- King Of Time / Touch On Time / Jobcan 的正式 API 拉取。

这些能力进入阶段 4、阶段 5、阶段 8。

## 2. 输入与输出边界

### 2.1 输入

输入来源：

- 管理员手动打卡。
- CSV 文件导入。
- Webhook 接收。
- 后续外部系统 API 拉取预留。

手动打卡输入字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| employeeId | 是 | 系统员工 ID |
| punchTime | 是 | 打卡时间，使用日本时区 |
| punchType | 是 | 出勤、退勤、休息开始、休息结束 |
| sourceSystem | 否 | 默认 MANUAL |
| deviceName | 否 | 手动录入来源说明 |
| note | 否 | 备注 |

CSV 导入第一版字段：

| 字段 | 必填 | 示例 | 说明 |
|---|---|---|---|
| externalEmployeeId | 是 | E000123 | 外部打卡系统员工 ID |
| punchTime | 是 | 2026-05-24 09:01:23 | 打卡时间 |
| punchType | 是 | CLOCK_IN | 打卡类型 |
| sourceSystem | 否 | CUSTOM | 来源系统，空值默认 CSV_IMPORT |
| sourceEventId | 否 | evt_001 | 来源事件 ID，用于去重 |
| deviceId | 否 | gate-01 | 设备 ID |
| deviceName | 否 | 东京本部门口 | 设备名称 |

Webhook 输入字段：

```json
{
  "tenantCode": "school001",
  "sourceSystem": "CUSTOM",
  "sourceEventId": "evt_202605240001",
  "externalEmployeeId": "E000123",
  "punchTime": "2026-05-24T09:01:23+09:00",
  "punchType": "CLOCK_IN",
  "deviceId": "device-01",
  "rawData": {
    "originalStatus": "出勤",
    "terminalName": "亀戸教室入口"
  }
}
```

### 2.2 输出

后端输出：

- 原始打卡记录。
- 导入批次结果。
- 员工匹配结果。
- 重复数据判断结果。
- 处理状态。
- 错误信息。
- 原始 payload。

前端输出：

- 打卡记录列表。
- 导入向导。
- 导入预览。
- 导入结果摘要。
- 右侧详情抽屉。
- 未匹配员工处理面板。
- 失败记录下载。

### 2.3 责任边界

阶段 3 只负责“事实数据进系统并可被人工整理”。

阶段 3 不负责把打卡记录计算成出勤结果。日次勤怠计算由阶段 4 负责。

## 3. 核心设计原则

### 3.1 原始数据永远保留

无论记录是否重复、失败、未匹配、已忽略，都必须保存原始 payload。后续排障和审计都依赖原始记录。

### 3.2 解析字段和原始 payload 分开

列表展示使用解析后的稳定字段，例如员工、打卡时间、打卡类型、来源、状态。详情里再展示原始 JSON，默认折叠。

### 3.3 所有来源进入同一张原始记录表

手动、CSV、Webhook 后续都进入 `punch_raw_log`。不同来源通过 `sourceSystem`、`sourceEventId`、`importBatchId` 区分。

### 3.4 用户先看结论，再看技术细节

页面首先展示：

- 成功多少。
- 失败多少。
- 重复多少。
- 未匹配多少。
- 下一步应该处理什么。

原始 JSON、异常堆栈、payload 只放在详情抽屉中。

### 3.5 未匹配必须给动作

员工未匹配不是死错误。页面必须直接提供：

- 绑定已有员工。
- 创建新员工。
- 忽略这条记录。

### 3.6 重复数据不打断导入

CSV 导入时遇到重复记录应跳过并计数，不应导致整批失败。

```text
PROCESSED

PENDING

UNMATCHED

PENDING
  ↓ 格式错误 / 字段缺失
ERROR

PENDING
  ↓ sourceEventId 重复
DUPLICATE

UNMATCHED / ERROR / PROCESSED
  ↓ 用户忽略
IGNORED
```

## 5. 数据与字段设计

### 5.1 punch_raw_log

用途：保存每一条原始打卡事实。

```sql
CREATE TABLE punch_raw_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    employee_id BIGINT,
    external_employee_id VARCHAR(100),
    source_system VARCHAR(50) NOT NULL,
    source_event_id VARCHAR(100),
    punch_time DATETIME NOT NULL,
    punch_type VARCHAR(30) NOT NULL,
    device_id VARCHAR(100),
    device_name VARCHAR(200),
    location_lat DECIMAL(10,7),
    location_lng DECIMAL(10,7),
    raw_payload CLOB,
    import_batch_id BIGINT,
    process_status VARCHAR(30) DEFAULT 'PENDING',
    error_message VARCHAR(500),
    ignored_reason VARCHAR(500),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (tenant_id, source_system, source_event_id)
);
```

字段说明：

| 字段 | 说明 |
|---|---|
| employee_id | 系统员工 ID，未匹配时为空 |
| external_employee_id | 外部系统员工 ID |
| source_system | MANUAL / CSV_IMPORT / WEBHOOK / CUSTOM 等 |
| source_event_id | 外部事件唯一 ID，用于去重 |
| punch_time | 打卡发生时间 |
| punch_type | CLOCK_IN / CLOCK_OUT / BREAK_START / BREAK_END |
| raw_payload | 原始 JSON 或 CSV 行转 JSON |
| import_batch_id | CSV 导入批次 |
| process_status | 当前处理状态 |
| error_message | 失败原因 |
| ignored_reason | 忽略原因 |

H2 第一版注意：

- H2 对 JSON 类型支持有限，开发态先用 `CLOB` 保存 JSON 字符串。
- 正式库如果使用 MySQL 或 PostgreSQL，可迁移为 JSON / JSONB。

### 5.2 punch_import_batch

用途：保存一次 CSV 导入的整体结果。

```sql
CREATE TABLE punch_import_batch (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    source_system VARCHAR(50),
    import_type VARCHAR(30),
    file_name VARCHAR(300),
    total_count INT DEFAULT 0,
    success_count INT DEFAULT 0,
    duplicate_count INT DEFAULT 0,
    unmatched_count INT DEFAULT 0,
    error_count INT DEFAULT 0,
    ignored_count INT DEFAULT 0,
    status VARCHAR(30) DEFAULT 'PROCESSING',
    started_at DATETIME,
    finished_at DATETIME,
    created_by BIGINT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

状态：

```text
PROCESSING 处理中
COMPLETED  完成
FAILED     整批失败
PARTIAL    部分成功
```

### 5.3 punch_source_config

用途：保存外部来源配置。阶段 3 只实现 `CUSTOM_WEBHOOK` 和 `CSV_IMPORT` 的配置展示，正式多系统接入放到阶段 8。

```sql
CREATE TABLE punch_source_config (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    source_system VARCHAR(50) NOT NULL,
    config_name VARCHAR(100),
    api_base_url VARCHAR(500),
    api_key VARCHAR(500),
    api_secret VARCHAR(500),
    webhook_secret VARCHAR(500),
    enabled TINYINT DEFAULT 1,
    config_json CLOB,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (tenant_id, source_system)
);
```

### 5.4 process_status 枚举

| 状态 | 中文 | 日文 | 说明 |
|---|---|---|---|
| PENDING | 待处理 | 処理待ち | 已入库，尚未处理 |
| PROCESSED | 已处理 | 処理済み | 已匹配员工并可用于后续计算 |
| UNMATCHED | 员工未匹配 | 従業員未紐付け | 外部员工 ID 找不到员工 |
| ERROR | 处理失败 | 処理失敗 | 字段格式错误或系统处理失败 |
| DUPLICATE | 重复数据 | 重複データ | 来源事件重复 |
| IGNORED | 已忽略 | 無視済み | 用户确认不再处理 |

### 5.5 可配置项

| 配置项 | 默认值 | 说明 |
|---|---|---|
| csvPreviewLimit | 10 | CSV 导入前预览行数 |
| duplicateKeyMode | sourceEventId | 第一版按 sourceSystem + sourceEventId 去重 |
| defaultSourceSystem | CSV_IMPORT | CSV 未传来源时使用 |
| rawPayloadMaxDisplayLength | 20000 | 前端原始 JSON 展示上限 |
| importMaxRows | 5000 | 单次 CSV 最大导入行数 |
| timezone | Asia/Tokyo | 打卡时间默认时区 |

```json
  "reason": "测试数据，不进入考勤计算"
}
```

### 6.8 重新处理记录

```http
POST /api/attendance/punch/logs/{id}/reprocess
```

用途：

- 员工绑定外部 ID 后，重新匹配未匹配记录。
- 修正来源字段后，重新处理错误记录。

### 6.9 绑定未匹配记录到员工

```http
POST /api/attendance/punch/logs/{id}/bind-employee
```

请求：

```json
{
  "employeeId": 12,
  "saveMapping": true
}
```

说明：

- `saveMapping=true` 时，将当前 `externalEmployeeId` 保存为员工外部打卡 ID 映射。
- 绑定成功后，该记录状态变为 `PROCESSED`。
- 同一外部 ID 的其他 `UNMATCHED` 记录可提示用户是否批量重新处理。

## 7. 后端处理规则

### 7.1 去重规则

优先使用：

```text
tenantId + sourceSystem + sourceEventId
```

如果 `sourceEventId` 为空，第一版生成弱去重键：

```text
sourceSystem + externalEmployeeId + punchTime + punchType
```

弱去重只用于 CSV 和 MANUAL，Webhook 必须要求 `sourceEventId`。

### 7.2 员工匹配规则

匹配顺序：

1. 使用 `externalEmployeeId` 查员工外部打卡 ID 映射。
2. 如果未匹配，尝试用员工编号精确匹配。
3. 如果仍未匹配，状态设为 `UNMATCHED`。

不做模糊匹配：

- 不按姓名模糊匹配。
- 不按假名模糊匹配。
- 不自动创建员工。

原因：打卡事实数据会影响工资和考勤，模糊匹配风险过高。

### 7.3 手动打卡规则

手动打卡必须选择系统员工，因此默认可直接 `PROCESSED`。

手动打卡的 `rawPayload` 仍需保存：

```json
{
  "source": "MANUAL",
  "createdBy": "admin",
  "note": "员工忘记打出勤卡"
}
```

### 7.4 CSV 解析规则

第一版只支持 UTF-8 CSV。

CSV 必须包含：

```text
externalEmployeeId,punchTime,punchType
```

允许空列：

```text
sourceSystem,sourceEventId,deviceId,deviceName
```

错误行不影响其他行导入。

### 7.5 Webhook 规则

阶段 3 Webhook 是自定义格式接收入口，不做外部系统签名适配。

第一版必须支持：

- `CUSTOM`
- `CSV_IMPORT`
- `MANUAL`

预留但不正式承诺：

- `KING_OF_TIME`
- `TOUCH_ON_TIME`
- `JOBCAN`

### 7.6 状态更新规则

- `PROCESSED` 可以被忽略，但必须保留原记录。
- `IGNORED` 可以重新处理。
- `DUPLICATE` 不参与后续日次计算。
- `UNMATCHED` 在绑定员工后可转为 `PROCESSED`。
- `ERROR` 在修正后可重新处理。

## 14. 风险点

### 14.1 CSV 格式过早复杂化

风险：一开始就兼容多个外部系统 CSV，会拖慢阶段 3。

处理：第一版只支持标准模板。其他来源在阶段 8 做适配器。

### 14.2 员工匹配误判

风险：如果按姓名模糊匹配，可能把打卡归到错误员工，影响工资。

处理：只做外部 ID 和员工编号精确匹配。

### 14.3 原始 JSON 太长影响页面

风险：详情抽屉展示大 payload 会卡顿。

处理：默认折叠，超过展示上限时提示下载或复制。

### 14.4 重复判断缺少 sourceEventId

风险：部分 CSV 没有事件 ID，强去重不可用。

处理：CSV 允许弱去重，但页面必须提示“该来源没有事件 ID，系统按员工 + 时间 + 类型辅助判断重复”。

### 14.5 和阶段 4 计算边界混淆

风险：用户可能以为打卡导入后已经完成日次计算。

处理：阶段 3 页面只显示“原始记录已处理”，不显示迟到早退结论。日次计算入口在阶段 4。
