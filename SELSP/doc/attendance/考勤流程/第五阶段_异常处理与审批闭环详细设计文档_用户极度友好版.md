# 第五阶段：异常处理与审批闭环详细设计文档

> 版本：v1.0  
> 目标阶段：阶段 5  
> 适用工程：SELATTENDANCE / SELSP / SELVUE  
> 文档定位：在阶段 4 日次勤怠计算与异常识别之后，补齐“异常被谁处理、如何提交、如何审批、如何留痕、何时锁定”的正式业务闭环。  
> 设计原则：延续当前考勤工作台风格、中日双语、一键启动、用户不需要理解数据库和规则细节，也能顺着页面完成异常处理与审批。

### 0.2 当前核心问题

问题 1：第四阶段已经能识别异常，但还没有“谁负责处理”。

系统现在能告诉管理员：

- 谁迟到
- 谁缺卡
- 谁缺勤
- 谁休日出勤

但还没有把这些异常转成正式业务单据，因此页面只能“看到异常”，不能“处理异常”。

问题 2：缺少员工说明与审批留痕。

真实勤怠场景里，员工经常需要解释：

- 忘记打卡
- 外勤未带卡
- 设备故障
- 代课 / 调岗 / 临时会议
- 休息补录

如果没有员工说明、审批意见和处理动作日志，后续月结和审计都不稳定。

问题 3：重算和审批边界还没建立。

第四阶段允许管理员重算日次结果，但当某条异常已经进入审批中或已审批通过后，系统不能继续把它当作自由可重算对象，否则前后数据会漂移。

问题 4：月结还没有前置锁定层。

第六阶段月结不能直接面对“仍可修改”的日次结果。第五阶段必须先把日次结果推进到：

- 待处理
- 审批中
- 已通过
- 已驳回
- 已锁定

这样第六阶段才能建立在稳定日结果之上。

### 0.3 当前字段 / 结构是否可以复用

可以复用：

- `attendance_daily`
  - 作为异常处理与审批的主承载对象。
- `attendance_exception`
  - 作为异常识别输入和待处理清单来源。
- `attendance_calc_log`
  - 作为审批前的计算依据说明。
- 员工主数据、部门、事业所
  - 作为审批筛选与权限维度。
- 现有工作台布局
  - 继续承接第五阶段工作区。
- 当前确认弹窗、共享 tip、右侧详情面板交互
  - 可延续用于审批、退回、锁定等操作。

仍然不足：

- `attendance_daily` 只有计算结果，没有审批状态和处理单生命周期。
- `attendance_exception` 只有异常事实，没有“由谁处理、什么时候处理、处理意见是什么”。
- 当前没有附件和补充说明结构。
- 当前没有“审批后回写日次结果”的业务桥。

### 0.4 开发前必须先修正的事项

1. 必须明确第五阶段只做“异常处理与审批闭环”，不提前混入第六阶段月次汇总和月结确认。
2. 必须定义“异常处理单”与“日次结果”的关系：
   - 是一条日次结果一张处理单；
   - 还是一条日次结果可关联多次处理动作。
3. 必须明确审批通过后哪些字段能回写到 `attendance_daily`，哪些只能写动作日志。
4. 必须先定义锁定边界：
   - 审批中是否允许重算；
   - 已通过是否允许重新发起；
   - 已锁定是否完全禁止修改。
5. 必须先定义第一版审批层级，避免一开始就做复杂多级流转。

## 1. 阶段目标

第五阶段目标是把第四阶段识别出来的异常，变成“可提交、可审批、可留痕、可锁定”的正式业务闭环。

本阶段完成后，用户应该可以：

- 看到哪些日次异常需要处理。
- 由员工或管理员提交异常说明。
- 选择处理类型：
  - 缺卡说明
  - 迟到说明
  - 早退说明
  - 缺勤说明
  - 无排班出勤说明
  - 人工修正申请
- 上传附件或填写补充备注。
- 进入审批列表，由管理者执行通过 / 驳回 / 退回补充。
- 审批通过后，把确认后的结果回写到日次结果。
- 查看完整处理日志和审批意见。
- 对已完成审批的记录执行锁定，作为后续月结输入。

本阶段不做：

- 月次汇总。
- 月结确认。
- 工资口径计算。
- 有休台账自动扣减。
- 多级跨组织复杂审批链。
- 手机端自助审批。

这些能力进入阶段 6 及后续阶段。

### 2.3 责任边界

第五阶段只负责“异常如何被处理和确认”。

第五阶段负责：

- 创建异常处理单。
- 接收员工说明。
- 接收管理员修正。
- 审批流转。
- 审批日志留痕。
- 审批后回写日次结果。
- 锁定可进入月结的稳定结果。

第五阶段不负责：

- 重新定义第四阶段基础计算规则。
- 生成月次汇总。
- 扣薪、补贴、津贴结算。
- 工资系统导出。

## 3. 核心设计原则

### 3.1 先把异常变成“单”，再谈审批

异常不能直接在日次结果表上随手改。必须先形成处理单，再通过处理单进入审批。

### 3.2 审批必须可追溯

任何通过、驳回、退回补充都必须留下：

- 谁操作
- 什么时间操作
- 改了什么
- 为什么改

### 3.3 第一版只做单级审批

第一版只做：

- 提交
- 审批通过
- 驳回
- 退回补充

不做复杂多级链路，先保证闭环稳定。

### 3.4 日次结果和处理单分层

- `attendance_daily` 保存最终业务结果。
- `attendance_case` 保存处理中的业务单据。

这样既能保留最终稳定结果，也能看到处理过程。

### 3.5 锁定优先于复杂权限

第一版先用“状态机 + 锁定”保证业务边界，不先引入过深 RBAC。

## 4. 总体方案

### 4.1 总体链路

第五阶段整体链路如下：

1. 第四阶段生成日次结果和异常。
2. 系统把异常结果暴露为“待处理”清单。
3. 员工或管理员创建异常处理单。
4. 审批人进入待审批列表查看详情。
5. 审批人执行通过 / 驳回 / 退回补充。
6. 若审批通过：
   - 回写 `attendance_daily`
   - 更新异常状态
   - 记录动作日志
7. 若日次结果已确认无误，可被锁定，供第六阶段月结使用。

### 4.2 推荐页面结构

继续沿用工作台三栏：

- 左侧：
  - 功能导航
  - 第五阶段入口“异常处理 / 审批”
- 中部：
  - 异常统计卡
  - 待处理 / 待审批切换
  - 异常列表
  - 批量操作条
- 右侧：
  - 日次详情
  - 原始打卡与排班摘要
  - 处理单时间线
  - 审批操作区

### 4.3 状态机总览

#### 4.3.1 处理单状态

| 状态 | 说明 |
|---|---|
| DRAFT | 草稿，尚未提交 |
| SUBMITTED | 已提交，待审批 |
| RETURNED | 被退回补充 |
| APPROVED | 已审批通过 |
| REJECTED | 已驳回 |
| CANCELLED | 已取消 |
| LOCKED | 结果已锁定 |

#### 4.3.2 日次结果处理状态

| 状态 | 说明 |
|---|---|
| UNHANDLED | 发现异常但尚未处理 |
| IN_REVIEW | 处理中 / 审批中 |
| RESOLVED | 已处理完成 |
| LOCKED | 已锁定，供月结使用 |

## 5. 异常处理与审批规则设计

### 5.1 可发起处理单的异常类型

第一版支持：

- 缺上班卡
- 缺下班卡
- 迟到
- 早退
- 缺勤
- 无排班出勤
- 休日出勤需补说明

### 5.2 默认处理动作

| 异常类型 | 默认动作建议 |
|---|---|
| 缺上班卡 | 提交缺卡说明或管理员补录 |
| 缺下班卡 | 提交缺卡说明或管理员补录 |
| 迟到 | 提交迟到说明 |
| 早退 | 提交早退说明 |
| 缺勤 | 提交缺勤说明或修正为请假 / 特殊情况 |
| 无排班出勤 | 提交临时出勤说明或转人工修正 |
| 休日出勤 | 提交休日出勤确认说明 |

### 5.3 审批通过后的回写规则

审批通过后允许回写：

- 最终上班时间
- 最终下班时间
- 最终休息分钟
- 最终状态
- 异常是否解除
- 审批结论说明

审批通过后不直接覆盖：

- 原始打卡记录
- 原始排班记录
- 计算日志历史记录

原始事实保留不动，审批只影响“最终业务结论”。

### 5.4 退回补充规则

退回补充后：

- 处理单状态变为 `RETURNED`
- 日次处理状态保持 `IN_REVIEW`
- 原审批意见写入动作日志
- 申请人可补充说明后再次提交

### 5.5 锁定规则

满足以下条件才允许锁定：

- 日次状态已确认
- 没有进行中的处理单
- 当前记录不在审批中

锁定后：

- 不允许直接编辑审批结果
- 不允许再次创建新的处理单，除非先解锁
- 第六阶段月结只能读取 `LOCKED` 或被允许纳入月结的稳定记录

## 7. 接口契约设计

### 7.1 异常列表

`GET /api/attendance/cases`

用途：

- 查待处理
- 查待审批
- 查已处理

主要参数：

| 参数 | 说明 |
|---|---|
| startDate | 开始日期 |
| endDate | 结束日期 |
| workplaceId | 事业所 |
| departmentId | 部门 |
| employeeKeyword | 员工搜索 |
| caseStatus | 处理单状态 |
| handlingStatus | 日次处理状态 |
| mineOnly | 仅看与我相关 |
| page | 页码 |
| pageSize | 每页条数 |

### 7.2 创建处理单

`POST /api/attendance/cases`

请求体示例：

```json
{
  "attendanceDailyId": 2143,
  "caseType": "MISSING_CLOCK_OUT",
  "applicantId": 1001,
  "applicantRole": "MANAGER",
  "reasonCategory": "DEVICE_ERROR",
  "reasonText": "终端在 18:00 左右断线，员工已口头确认离岗。",
  "expectedResolution": "请按 18:05 作为下班时间处理。"
}
```

### 7.3 处理单详情

`GET /api/attendance/cases/{id}`

返回：

- 日次结果摘要
- 原始打卡摘要
- 当前处理单
- 附件
- 动作日志时间线

### 7.4 提交审批动作

`POST /api/attendance/cases/{id}/actions`

请求体示例：

```json
{
  "actionType": "APPROVE",
  "approverId": 9001,
  "comment": "同意按设备故障处理。",
  "patchPayload": {
    "actualClockOut": "2026-05-20T18:05:00+09:00",
    "finalStatus": "NORMAL",
    "finalExceptionFlag": false
  }
}
```

### 7.5 批量审批

`POST /api/attendance/cases/batch-actions`

适用场景：

- 批量通过同类缺卡
- 批量退回补充

### 7.6 锁定与解锁

- `POST /api/attendance/daily/{id}/lock`
- `POST /api/attendance/daily/{id}/unlock`

第一版建议仅管理员可见。

## 8. 页面与交互设计

### 8.1 左侧导航

  - 通过后将回写日次结果
  - 驳回后保留异常

## 10. 风险点

1. 审批通过后回写哪些字段，如果定义不清，会造成“原始事实”和“最终结论”混淆。
2. 如果第五阶段不做锁定，月结阶段会面对持续变动的日结果。
3. 如果一开始就做多级审批，会把本阶段复杂度拉高，影响一键启动验证。
4. 如果附件上传先做成复杂外部存储耦合，可能拖慢本阶段闭环；第一版可先保留简单文件引用或本地开发模式。
5. 如果审批中仍允许任意重算，可能出现审批意见与最终日结果不一致。

## 11. 验证方案

### 11.1 后端验证

- 创建处理单
- 提交审批
- 通过回写日次结果
- 驳回保持异常
- 退回补充
- 锁定 / 解锁

- 打开右侧详情
- 提交一条处理单
- 执行通过 / 驳回 / 退回
- 状态变化正确回显
- 锁定后按钮状态变化

### 11.3 真实页面截图验证

至少保留：

- 待处理列表截图
- 详情与时间线截图
- 审批弹窗截图
- 通过后的状态变化截图

## 12. 最小可交付范围

第五阶段第一轮最小可交付范围建议：

1. 单级审批。
2. 只支持文本说明，附件可先预留。
3. 只支持管理员或主管审批。
4. 只支持日次异常主路径：
   - 缺卡
   - 迟到
   - 早退
   - 缺勤
5. 支持审批通过后回写 `attendance_daily`。
6. 支持锁定。

先不做：

- 复杂多级审批
- 批量附件
- 移动端提交
- 月结联动

## 13. Codex 开发提示词

如果后续要直接进入第五阶段代码开发，建议按以下顺序：

1. 先补数据库表：
   - `attendance_case`
   - `attendance_case_action_log`
   - `attendance_case_attachment`
   - `attendance_daily` 扩展字段
2. 再做后端最小闭环：
   - 列表
   - 详情
   - 创建处理单
   - 提交审批动作
   - 锁定 / 解锁
3. 再做前端工作区：
   - 统计卡
   - 列表
   - 详情抽屉
   - 审批弹窗
4. 最后做真实页面截图和审批状态回归验证。

开发时必须注意：

- 不要把第六阶段月结逻辑混进来。
- 不要修改原始打卡和原始排班事实。
- 审批通过只回写最终业务结论和处理状态。
- 代码完成后必须做测试和真实页面验证。

## 14. 本阶段完成定义

满足以下条件，才视为第五阶段完成：

1. 异常日次可以创建正式处理单。
2. 处理单可以提交审批。
3. 审批人可以执行通过 / 驳回 / 退回补充。
4. 审批动作有完整时间线留痕。
5. 审批通过后能正确回写日次结果。
6. 日次结果支持锁定。
7. 前端页面能完整演示待处理、待审批、详情、审批和状态变化。
8. 后端测试、前端构建和真实页面截图验证全部通过。
