# 第四阶段：日次勤怠计算与异常处理详细设计文档

> 版本：v1.0  
> 目标阶段：阶段 4  
> 适用工程：SELATTENDANCE / SELSP / SELVUE  
> 文档定位：在阶段 1 基础资料、阶段 2 排班管理、阶段 3 打卡接收之后，补齐“按天生成勤怠结果并处理异常”的正式闭环。  
> 设计原则：延续当前考勤工作台风格、中日双语、一键启动、用户不需要理解技术细节也能完成主流程。

### 0.2 当前核心问题

问题 1：系统已经有“计划排班”和“原始打卡”，但还没有“每日结论”。

当前管理员能看到员工应该上什么班，也能看到员工实际打了什么卡，但仍然需要人工自己判断这一天是否迟到、早退、缺卡、缺勤、休日出勤。

问题 2：异常没有统一出口。

第三阶段能识别原始记录是否失败或未匹配，但还没有把“有排班无打卡”“有打卡无排班”“只打了上班卡没打下班卡”集中成日次异常。

问题 3：后续审批和月结没有中间层承接。

第五阶段审批、第六阶段月次汇总都不应该直接面对 `shift_schedule` 和 `punch_raw_log`。它们必须基于稳定的 `attendance_daily` 结果工作。

问题 4：当前用户路径停在“我看到数据了”，还没有推进到“系统已经告诉我结果”。

极度友好版要求用户点进页面后，第一眼看到的是“今天谁异常、为什么异常、建议怎么处理”，而不是要求管理员自己拼凑排班与打卡。

### 0.3 当前字段 / 结构是否可以复用

可以复用：

- `shift_schedule`
  - 作为日次计算的计划班次输入。
- `punch_raw_log`
  - 作为日次计算的原始打卡输入。
- 员工主数据、部门、事业所
  - 作为筛选和展示维度。
- 现有工作台布局
  - 继续承接第四阶段页面，不新增全新后台体系。
- 当前中日双语字典组织方式
  - 继续在 `i18nMessages.js` 中补齐第四阶段文案。
- 当前确认弹窗、浮层提示、左右分栏、右侧详情面板交互方式
  - 可以直接延续。

仍然不足：

- `shift_schedule` 只表示计划，不适合保存计算结果。
- `punch_raw_log` 只表示原始事实，不适合直接作为前台业务结论。
- 当前没有“哪一条打卡被选进了这次计算”的关联结构。
- 当前没有“本次计算为什么得出迟到 8 分钟”的可追溯日志结构。

### 0.4 开发前必须先修正的事项

1. 必须先明确第四阶段只做“日次结果和异常”，不提前混入月次汇总、审批流和工资导出。
2. 必须统一第四阶段只读取 `punch_raw_log.process_status = PROCESSED` 的记录，排除 `UNMATCHED / ERROR / IGNORED / DUPLICATE`。
3. 必须明确第一版日次计算的默认规则，避免一开始就引入过深的日本高级工时规则。
4. 必须先定义“多条打卡如何配对”和“没有排班但有打卡怎么处理”的默认口径，否则接口和页面会各自解释。
5. 必须先定义重算边界：单日重算、日期范围重算、按筛选批量重算分别落到哪些接口。

## 1. 阶段目标

第四阶段目标是让系统根据排班和原始打卡，自动生成每天的勤怠结果，并把异常集中展示给管理员处理。

本阶段完成后，用户应该可以：

- 查看某天、某部门、某员工的日次勤怠结果。
- 看到每天的主状态：
  - 正常
  - 迟到
  - 早退
  - 缺勤
  - 缺上班卡
  - 缺下班卡
  - 无排班出勤
  - 有排班无打卡
  - 休日出勤
- 查看当天的排班、打卡、工作时长、休息时长、迟到分钟、早退分钟。
- 查看这条结果是怎么计算出来的。
- 对异常记录执行重新计算。
- 跳转到补卡或后续审批入口。
- 集中查看异常列表，并按严重度优先处理。

本阶段不做：

- 月次汇总。
- 月结锁定。
- 审批通过后的正式补卡流程闭环。
- 有休台账结转。
- 工资导出。
- 法定残业、深夜、休日等完整工资口径结算。

这些能力进入阶段 5 及后续阶段。

## 2. 输入与输出边界

### 2.1 输入

第四阶段输入来源：

- 第二阶段的排班数据。
- 第三阶段的原始打卡数据。
- 第一阶段的员工与默认规则数据。
- 管理员手动发起的单日重算或批量重算请求。

主输入字段如下：

#### 2.1.1 计算主输入

| 字段 | 必填 | 说明 |
|---|---|---|
| tenantId | 是 | 租户 ID |
| employeeId | 是 | 员工 ID |
| workDate | 是 | 工作日期 |
| shiftScheduleId | 否 | 当天排班 ID，允许为空 |
| processedPunchLogs | 否 | 当天已处理原始打卡记录列表 |

#### 2.1.2 打卡输入字段

| 字段 | 必填 | 说明 |
|---|---|---|
| punchRawLogId | 是 | 原始打卡记录 ID |
| punchTime | 是 | 打卡时间 |
| punchType | 是 | CLOCK_IN / CLOCK_OUT / BREAK_START / BREAK_END |
| sourceSystem | 是 | MANUAL / CSV_IMPORT / WEBHOOK / 后续扩展 |
| employeeId | 是 | 已匹配员工 ID |

#### 2.1.3 排班输入字段

| 字段 | 必填 | 说明 |
|---|---|---|
| shiftScheduleId | 是 | 排班主键 |
| workDate | 是 | 工作日期 |
| shiftTemplateId | 否 | 班次模板 ID |
| startTime | 否 | 计划开始时间 |
| endTime | 否 | 计划结束时间 |
| breakMinutes | 否 | 计划休息分钟 |
| workDayType | 否 | WORKDAY / HOLIDAY / LEAVE / OFF |

### 2.2 输出

后端输出：

- `attendance_daily` 日次结果。
- `attendance_exception` 异常记录。
- `attendance_calc_log` 计算过程日志。
- 单日 / 批量重算结果摘要。

前端输出：

- 日次勤怠列表。
- 异常统计卡片。
- 日次详情抽屉。
- 计算过程说明面板。
- 异常处理建议入口。

### 2.3 责任边界

第四阶段只负责“把计划 + 打卡”转换为“每天结果”。

第四阶段负责：

- 读取排班。
- 读取有效打卡。
- 配对打卡。
- 计算基础工作时长。
- 计算迟到、早退、缺卡、缺勤、无排班出勤。
- 生成日结果与异常。
- 提供重算能力和解释能力。

第四阶段不负责：

- 最终审批修正。
- 最终月次汇总。
- 工资口径结算。
- 有休台账变更。

## 3. 核心设计原则

### 3.1 先给结论，再给过程

页面第一眼必须让管理员看到：

- 今天谁异常。
- 异常类型是什么。
- 严重度如何。
- 下一步建议是什么。

点击详情后再展示排班、打卡和计算过程。

### 3.2 计算结果必须可追溯

任何一条日次结果都必须能回答：

- 这天用了哪条排班。
- 这天选中了哪些打卡。
- 为什么是迟到 8 分钟，不是 5 分钟。
- 为什么被判定为缺下班卡。

### 3.3 默认规则先稳定，再逐步复杂化

第四阶段第一版只实现稳定的基础判断：

- 出勤 / 退勤配对
- 休息分钟
- 工作分钟
- 迟到
- 早退
- 缺勤
- 缺卡
- 无排班出勤

完整的日本复杂工时拆分先放后续阶段。

### 3.4 多来源打卡统一处理

不区分手动、CSV、Webhook 来源的前端展示口径。只要 `process_status = PROCESSED`，都进入日次计算。

### 3.5 异常必须给处理动作

异常不是只读标签。每个异常都必须带有至少一个可执行动作：

- 去补卡
- 去审批
- 重新计算
- 查看原始打卡

### 3.6 重算必须可控

不能每次修改打卡都全量重算所有员工所有日期。必须支持：

- 单日单人重算
- 单员工日期范围重算
- 按筛选条件批量重算

## 5. 日次计算规则设计

### 5.1 计算输入选取规则

第四阶段第一版只取：

- 当天对应员工的排班记录 0 或 1 条。
- 当天对应员工、状态为 `PROCESSED` 的原始打卡记录。

排除：

- `UNMATCHED`
- `ERROR`
- `IGNORED`
- `DUPLICATE`

### 5.2 打卡配对规则

默认配对规则：

1. `CLOCK_IN`
   - 取当天最早一条作为实际上班打卡。
2. `CLOCK_OUT`
   - 取当天最晚一条作为实际下班打卡。
3. `BREAK_START / BREAK_END`
   - 按时间先后配对。
   - 第一版如果配对不完整，先记录异常日志，但不阻断整条日次生成。

### 5.3 工作分钟计算规则

```text
实际工作分钟 = (实际下班 - 实际上班) - 实际休息分钟
```

如果没有完整上下班配对：

- 只缺上班卡：
  - `status = MISSING_CLOCK_IN`
- 只缺下班卡：
  - `status = MISSING_CLOCK_OUT`
- 两边都缺且有排班：
  - `status = NO_PUNCH`

### 5.4 迟到早退规则

第一版默认规则：

- 计划开始时间之后打上班卡，则记迟到。
- 计划结束时间之前打下班卡，则记早退。
- 第一版不做弹性班次窗口。

公式：

```text
late_minutes = max(0, actual_clock_in - scheduled_start_time)
early_leave_minutes = max(0, scheduled_end_time - actual_clock_out)
```

### 5.5 缺勤规则

满足以下条件时判定缺勤：

- 当天存在工作排班。
- 当天无任何有效打卡。
- 排班类型不是休息、不是有休。

### 5.6 无排班出勤规则

满足以下条件时判定：

- 当天没有排班。
- 但存在有效打卡。

状态：

- `NO_SCHEDULE`

并同时生成异常：

- `NO_SCHEDULE_PUNCH`

### 5.7 休日 / 休息 / 有休规则

第一版口径：

- `OFF / REST`
  - 有打卡则标记 `HOLIDAY_WORK`
  - 无打卡则保留休息状态，不记异常
- `LEAVE`
  - 有打卡则标记异常，待后续审批阶段处理
  - 无打卡则显示请假日，不记迟到早退

### 5.8 主状态优先级

一条日次结果如果同时满足多个条件，主状态按以下优先级显示：

```text
MISSING_CLOCK_IN / MISSING_CLOCK_OUT
  > ABSENCE
  > NO_SCHEDULE
  > LATE / EARLY_LEAVE
  > HOLIDAY_WORK
  > NORMAL
```

### 5.9 可配置参数与默认值

第四阶段第一版允许配置以下参数：

| 配置项 | 默认值 | 说明 |
|---|---|---|
| lateGraceMinutes | 0 | 迟到宽限分钟 |
| earlyLeaveGraceMinutes | 0 | 早退宽限分钟 |
| autoRecalculateOnPunchChange | true | 打卡变动后是否自动重算 |
| autoRecalculateOnScheduleChange | true | 排班变动后是否自动重算 |
| maxBatchRecalculateDays | 31 | 单次批量重算最大日期跨度 |

第一版建议先落在后端常量或租户默认配置，不要求前台开放复杂配置页面。

## 6. 数据与字段设计

### 6.1 数据表：attendance_daily

```sql
CREATE TABLE attendance_daily (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    employee_id BIGINT NOT NULL,
    work_date DATE NOT NULL,

    shift_schedule_id BIGINT,
    work_day_type VARCHAR(30) DEFAULT 'WORKDAY',

    scheduled_start_time DATETIME,
    scheduled_end_time DATETIME,
    scheduled_break_minutes INT DEFAULT 0,
    scheduled_work_minutes INT DEFAULT 0,

    actual_clock_in DATETIME,
    actual_clock_out DATETIME,
    actual_break_minutes INT DEFAULT 0,
    actual_work_minutes INT DEFAULT 0,

    late_minutes INT DEFAULT 0,
    early_leave_minutes INT DEFAULT 0,
    absence_minutes INT DEFAULT 0,

    normal_work_minutes INT DEFAULT 0,
    overtime_minutes INT DEFAULT 0,
    legal_overtime_minutes INT DEFAULT 0,
    night_work_minutes INT DEFAULT 0,
    holiday_work_minutes INT DEFAULT 0,

    status VARCHAR(30) DEFAULT 'NORMAL',
    approval_status VARCHAR(30) DEFAULT 'NONE',
    exception_flag TINYINT DEFAULT 0,
    locked TINYINT DEFAULT 0,

    calculated_at DATETIME,
    calc_version VARCHAR(50),
    calc_message VARCHAR(500),

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE KEY uk_daily (tenant_id, employee_id, work_date)
);
```

字段说明：

- `calc_version`
  - 记录当前结果使用的计算版本，便于后续规则升级后的重算追溯。
- `calc_message`
  - 记录简短结论，例如“按 2 条有效打卡生成结果”。

### 6.2 数据表：attendance_exception

```sql
CREATE TABLE attendance_exception (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    employee_id BIGINT NOT NULL,
    work_date DATE NOT NULL,
    attendance_daily_id BIGINT,

    exception_type VARCHAR(50) NOT NULL,
    exception_level VARCHAR(30) DEFAULT 'WARN',
    status VARCHAR(30) DEFAULT 'OPEN',
    message VARCHAR(500),
    suggested_action VARCHAR(100),

    resolved TINYINT DEFAULT 0,
    resolved_by BIGINT,
    resolved_at DATETIME,

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

### 6.3 数据表：attendance_calc_log

```sql
CREATE TABLE attendance_calc_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    tenant_id BIGINT NOT NULL,
    employee_id BIGINT NOT NULL,
    work_date DATE NOT NULL,
    attendance_daily_id BIGINT,

    trigger_type VARCHAR(30) NOT NULL,
    trigger_ref_id BIGINT,
    calc_status VARCHAR(30) NOT NULL,
    step_name VARCHAR(100) NOT NULL,
    step_message VARCHAR(1000),
    payload_json JSON,

    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

用途：

- 记录“这次为什么判迟到”“用了哪些打卡”“哪一步跳过了哪条记录”。
- 用于前端详情抽屉展示可读计算过程。

### 6.4 可复用字段与新增字段边界

可以直接复用：

- `shift_schedule` 的计划时间与班次类型字段。
- `punch_raw_log` 的员工、时间、类型、来源字段。
- 员工、部门、事业所主数据。

必须新增：

- `attendance_daily`
- `attendance_exception`
- `attendance_calc_log`

原因：

- 计算结果、异常结果、计算过程都不应回写污染原始打卡表。

## 7. 接口契约设计

### 7.1 日次列表查询

```http
GET /api/attendance/daily
```

查询参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| startDate | 是 | 开始日期 |
| endDate | 是 | 结束日期 |

## 10. 风险点

### 10.1 打卡跨日导致日期归属错误

风险：

- 夜班员工可能在次日凌晨打下班卡，简单按自然日取最晚卡会误算。

处理：

- 第一版在文档和页面明确：夜班复杂跨日规则先按最小口径处理。
- 夜班完整跨日配对列为第四阶段后续增强项或阶段 4.2。

### 10.2 多次打卡导致配对歧义

风险：

- 同一天多次上班卡或下班卡时，可能存在选择错误。

处理：

- 第一版固定使用“最早上班卡 + 最晚下班卡”。
- 计算日志必须保留被选中与被忽略的打卡信息。

### 10.3 页面把日次结论误当最终工资结论

风险：

- 用户可能以为日次结果已经等同月结工资结果。

处理：

- 页面说明中明确：当前为日次勤怠结果，不代表最终工资结算。

### 10.4 自动重算过多导致性能压力

风险：

- 大批量导入后同步全量重算会拖慢接口。

处理：

- 日期范围批量重算改为异步任务或分批执行。
- 第一版限制单次日期跨度默认不超过 31 天。
