# 第六阶段：月次汇总与月结详细设计文档

> 版本：v1.0  
> 目标阶段：阶段 6  
> 适用工程：SELATTENDANCE / SELSP / SELVUE  
> 文档定位：在阶段 5 已完成“异常处理、审批、锁定”之后，把稳定的日次结果汇总为月次结果，并形成可确认、可反结、可导出的正式月结闭环。  
> 设计原则：继续沿用当前考勤工作台风格、中日双语、一键启动、用户极度友好；即使不理解数据库和结算术语，也能顺着页面完成“看月汇总 -> 检查异常 -> 确认月结 -> 导出结果”。

### 0.2 当前核心问题

问题 1：日次结果已经稳定，但还没有沉淀成月次结果。

当前系统已经能给出每天的结果：

- 正常
- 迟到 / 早退
- 缺卡
- 缺勤
- 无排班打卡
- 审批修正后的最终状态

但管理员还不能直接看到：

- 这个员工本月总共出勤多少天
- 本月迟到几次
- 本月早退几次
- 本月缺勤几次
- 本月缺卡几次
- 本月休日日数 / 有休日数

问题 2：缺少正式月结状态。

现在第五阶段已经能锁定单日，但没有“整个月份已经结算确认”的状态，因此：

- 月次结果还可能被随意重算
- 导出的月报口径没有冻结点
- 无法告诉业务方“这份月报已经确认”

问题 3：没有“不可月结”的阻塞清单。

真实业务里，一个月不能直接月结，常见原因是：

- 还有未处理异常
- 还有未锁定日次
- 有员工本月数据缺失
- 有跨月修正尚未确认

如果没有月结前阻塞清单，管理员只能自己翻日次结果，非常低效。

问题 4：导出还停留在日级和排班级。

当前已有排班导出，但月次汇总还没有：

- 月度汇总导出
- 部门月报导出
- 事业所月报导出

这会导致系统已经能算，但不能交付正式月报。

### 0.3 第六阶段与第五阶段的边界

第五阶段负责：

- 识别异常
- 提交说明
- 审批处理
- 回写日次最终结果
- 锁定单日

第六阶段负责：

- 按月汇总稳定后的日次结果
- 判断本月是否可结
- 确认月结
- 必要时反结
- 导出月报

第六阶段不再处理：

- 员工异常说明正文编辑
- 审批流转细节
- 原始打卡清洗
- 排班网格编辑

这些都继续留在前面阶段。

### 0.4 开发前必须先修正的事项

1. 必须明确第六阶段只做“月次汇总与月结”，不提前混入工资核算。
2. 必须定义“月结确认后哪些能力被冻结”，例如：
   - 是否禁止月内日次重算；
   - 是否禁止新增异常单；
   - 是否允许反结后恢复编辑。
3. 必须明确月次统计口径优先使用：
   - `attendance_daily.final_*`
   - 若 final 为空，则回退原始日次结果。
4. 必须定义不可月结的阻塞规则。
5. 必须明确第一版导出只做月汇总，不直接做薪资接口对接。

## 1. 阶段目标

第六阶段目标是把第五阶段已经稳定、可锁定的日次结果，汇总成正式月次结果，并建立“可结 / 已结 / 反结 / 导出”的月度闭环。

本阶段完成后，用户应该可以：

- 选择某个月查看月次汇总。
- 按员工、部门、事业所查看月度结果。
- 看到月度核心指标：
  - 出勤天数
  - 排班天数
  - 正常天数
  - 迟到次数
  - 早退次数
  - 缺卡次数
  - 缺勤次数
  - 异常天数
  - 有休日数
  - 休息日数
- 看到本月是否可结。
- 如果不可结，直接看到阻塞原因。
- 对某员工月次执行重算。
- 对整个部门 / 事业所 / 全公司执行范围重算。
- 对月份执行“确认月结”。
- 对已结月份执行“反结”。
- 导出月度汇总结果。

本阶段不做：

- 工资金额计算。
- 加班费金额计算。
- 社保 / 税务计算。
- 银行代发文件生成。
- 复杂跨月结转规则。
- 多公司统一总账接口。

这些能力进入后续阶段。

## 3. 业务规则

### 3.1 月次统计口径

第一版采用“按日聚合”的稳定口径。

| 统计项 | 口径 |
|---|---|
| scheduledDays | 当月有计划班次的天数 |
| attendanceDays | 当月最终状态属于正常出勤或有效出勤的天数 |
| lateCount | 当月最终状态含迟到的次数 |
| earlyLeaveCount | 当月最终状态含早退的次数 |
| missingPunchCount | 当月最终状态含缺卡的次数 |
| absenceCount | 当月最终状态为缺勤的次数 |
| exceptionDays | 当月 `exception_flag = 1` 或仍存在未闭环异常的天数 |
| paidLeaveDays | 当月最终状态为有休的天数 |
| restDays | 当月最终状态为休息 / 休日的天数 |

### 3.2 月次统计优先级

统计时字段优先级固定为：

1. `attendance_daily.final_*`
2. 若 final 为空，则回退原始计算结果

这样可以保证：

- 审批通过后的修正结果能进入月次
- 未审批修改的原始结果仍可参与汇总

### 3.3 不可月结阻塞规则

第一版阻塞规则：

1. 月内存在 `handling_status != RESOLVED` 的日次。
2. 月内存在 `exception_flag = 1` 且未审批关闭的日次。
3. 月内存在要求锁定但 `locked_flag = 0` 的异常日次。
4. 月内存在关键主数据缺失导致日次不可归属。

阻塞结果要直接展示给用户，不能只返回布尔值。

### 3.4 月结确认规则

月结确认后：

- 该范围内月次状态改为 `CLOSED`
- 对应月次记录写入 `closed_at / closed_by`
- 默认禁止直接重算
- 默认禁止继续修改本月最终结果

### 3.5 反结规则

反结后：

- 月次状态改为 `REOPENED`
- 允许重新执行月次重算
- 允许补做异常审批与锁定
- 必须记录反结原因

反结权限第一版仅开放给管理员。

### 4.4 是否需要新增月次阻塞表

第一版不单独建阻塞表，阻塞原因运行时动态生成即可。

原因：

- 阻塞信息主要来自日次当前状态
- 一旦日次审批/锁定变化，阻塞结果就会变化
- 动态生成更稳定，不容易产生脏缓存

若后续需要审计某次月结前的阻塞快照，再考虑新增：

- `attendance_monthly_block_snapshot`

## 5. 后端接口设计

### 5.1 月次列表

`GET /api/attendance/monthly`

参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| yearMonth | 是 | 月份 |
| workplaceId | 否 | 事业所 |
| departmentId | 否 | 部门 |
| employeeKeyword | 否 | 员工检索 |
| closeStatus | 否 | 月结状态 |
| onlyBlocked | 否 | 只看不可结 |
| page | 是 | 页码 |
| pageSize | 是 | 每页条数 |

返回：

- 月次分页列表
- 顶部汇总卡

### 5.2 月次详情

`GET /api/attendance/monthly/{id}`

返回：

- 主汇总结果
- 指标明细
- 阻塞原因
- 月内日次快照
- 最近动作日志

### 5.3 月次重算

`POST /api/attendance/monthly/recalculate`

用途：

- 单员工重算
- 部门重算
- 事业所重算
- 整月重算

第一版同步执行即可，后续若耗时变长再改批任务。

### 5.4 月结确认

`POST /api/attendance/monthly/close`

逻辑：

1. 检查是否存在阻塞项。
2. 无阻塞则把目标范围状态改为 `CLOSED`。
3. 写动作日志。

### 5.5 反结

`POST /api/attendance/monthly/reopen`

逻辑：

1. 检查权限。
2. 将月次状态改为 `REOPENED`。
3. 写动作日志。

### 5.6 月报导出

`POST /api/attendance/monthly/export`

第一版导出：

- CSV
- Excel

字段口径与列表一致。

## 8. 权限与状态控制

第一版权限建议：

| 角色 | 权限 |
|---|---|
| EMPLOYEE | 只读自己的月次结果 |
| MANAGER | 查看所辖范围月次，执行导出 |
| ADMIN | 重算、月结、反结、导出 |

第一版状态机：

- `OPEN`
- `CLOSABLE`
- `CLOSED`
- `REOPENED`

说明：

- `OPEN`：已经汇总，但还有阻塞项
- `CLOSABLE`：已无阻塞，可以月结
- `CLOSED`：已确认月结
- `REOPENED`：已反结，重新开放

## 9. 与前面阶段的耦合点

### 9.1 与第四阶段耦合

第六阶段必须依赖第四阶段的日次结果字段。

### 9.2 与第五阶段耦合

第六阶段必须依赖第五阶段的：

- 审批最终结果
- 锁定状态
- 异常是否已关闭

### 9.3 与后续阶段耦合

第七阶段如进入薪资或外部报表接口时，应优先读取：

- `attendance_monthly`

而不是重新从日次层重复聚合。

## 11. 验证方案

### 11.1 后端验证

至少覆盖：

1. 月次汇总生成。
2. 审批通过后的日次能正确进入月次统计。
3. 未关闭异常会阻塞月结。
4. 锁定日次缺失会阻塞月结。
5. 月结成功后状态变为 `CLOSED`。
6. 反结后状态变为 `REOPENED`。

### 11.2 前端验证

至少覆盖：

1. 月次列表加载。
2. 月次详情切换。
3. 不可结原因展示。
4. 月结按钮启用 / 禁用。
5. 反结交互。
6. 导出入口显示。

### 11.3 真实业务验证样例

建议准备：

- 一名完全正常员工
- 一名迟到员工
- 一名存在已审批缺卡修正员工
- 一名仍有未处理异常员工

然后验证：

- 正常员工可直接月结
- 已审批修正员工统计正确
- 未处理异常员工阻塞月结

## 12. 第一版明确不做的事项

第一版不做：

- 按工时换算工资
- 深夜加班金额
- 法定 / 所定外加班金额
- 假勤余额自动联动
- 跨法人集中月结
- 审批后自动推送外部工资系统

这样可以确保第六阶段聚焦在：

- 月次汇总
- 月结确认
- 反结
- 导出

不让阶段目标失焦。

## 14. 阶段结论

第六阶段的本质不是“再做一张月报页面”，而是把前五阶段已经沉淀下来的稳定日次结果，正式变成“可确认、可冻结、可导出”的月度结果层。

只有完成这个阶段，考勤系统才真正具备：

- 日级闭环
- 异常闭环
- 月级闭环

这样后面的薪资、总账、外部对接才有稳定基础。
