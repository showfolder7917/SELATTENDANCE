# SELSP Vue工程架构标准

## 1. 文档定位

本文档是 `SELATTENDANCE/SELVUE` 及其后续所有 Vue 前端工程的通用架构标准。

当前项目工程唯一正式主参照不是 `SELTEMPLATE`，而是：

- `/Users/showfolder/Documents/workSpace/SELF/SELATTENDANCE/SELVUE/src/projects/attendance`
- 新前端模块必须优先参照 `attendance` 的目录、命名、工作台布局、国际化和主题接法
- 主题来源依赖仍然单独参照 `SELTHEME`，但业务工程结构不再以模板工程为主基线

作用不是描述某一个具体页面，而是统一以下内容：

- 工程目标
- 目录与分层约束
- 状态与服务边界
- 主题与组件复用方式
- 测试规范
- 面向自动 bug 修复的演进标准

## 2. 架构目标

- 可快速新增页面和业务模块，而不破坏既有结构。
- 可统一状态组织、接口接入、主题和验证方式。
- 可支持后续自动 bug 定位、自动页面回归和自动修复升级。
- 可明确区分“项目工程”“主题工程”“通用规范”三层边界。

## 3. 技术基线

- Vue 3
- Vite
- Composition API
- 原生 Fetch 或统一 request 包装
- CSS Variables
- 标准页面验证与构建验证

## 4. 目录标准

推荐目录结构如下：

```text
SELVUE/
├─ package.json
├─ vite.config.js
├─ 打开XXX前端.command
├─ 一键启动XXX全套.command
├─ public/
├─ src/
│  ├─ main.js
│  ├─ App.vue
│  ├─ style.css
│  ├─ views/
│  ├─ components/
│  ├─ composables/
│  ├─ services/
│  ├─ constants/
│  └─ assets/
└─ doc/
```

目录约束：

- `views` 只放页面级视图。
- `components` 只放可复用界面块。
- `composables` 只放页面状态、派生、动作和副作用封装。
- `services` 只放接口访问、缓存和桥接适配。
- `constants` 只放稳定配置、枚举、注入键和导航定义。
- `doc` 只放项目设计、接口和实施文档。
- 工程根目录若存在本地运行需求，必须沉淀正式 `command` 启动脚本，而不是只保留 `npm run dev` 口头说明。

## 4.1 启动器标准

### 4.1.1 脚本类型

Vue 前端工程默认至少应定义以下两类启动脚本：

- 单前端脚本：只负责启动当前 Vue 工程并打开页面。
- 全套脚本：当页面依赖本地后端或其他本地服务时，负责按依赖顺序启动前端与后端。

若后端工程由当前前端体系一并维护，则还应存在：

- 单后端脚本：只负责启动配套后端服务，并由当前脚本托管后端生命周期。

### 4.1.2 脚本职责

启动脚本至少要承担这些职责：

- 明确打印项目目录和访问地址。
- 接管目标端口，发现旧进程时先停止，再由当前脚本重新拉起。
- 首次运行若依赖缺失，应自动安装依赖。
- 关闭脚本窗口时，连同当前脚本拉起的前后端子进程一并停止。
- 启动失败时输出最近日志，不能只报“启动失败”。

### 4.1.3 脚本命名建议

推荐使用显式中文命名，便于业务方直接双击使用：

- `打开XXX前端.command`
- `启动XXX后端服务.command`
- `一键启动XXX全套.command`

### 4.1.4 联调桥接要求

若 Vue 页面依赖本地后端联调，则前端工程必须同时定义桥接策略：

- 开发态默认优先走同源相对路径，例如 `/api`。
- `vite.config.js` 中必须补正式代理规则，把相对路径转发到真实本地后端端口。
- 禁止把开发态默认请求长期写死成浏览器直接跨域访问 `http://127.0.0.1:xxxx`，否则双击启动后容易误回退本地 mock。

### 4.1.5 启动器验证要求

每次新增或修改启动器后，至少要做：

- 脚本语法检查。
- 前端构建验证。
- 单前端脚本真实启动验证。
- 单后端脚本真实启动验证。
- 全套脚本顺序启动验证。
- 关闭全套脚本后的生命周期回收验证。

## 5. 分层标准

### 5.1 App 壳层

职责：

- 挂载全局样式
- 提供应用级上下文
- 编排整体壳布局

约束：

- 不直接承载完整业务逻辑
- 不直接散落接口请求

### 5.2 View 层

职责：

- 承接页面布局
- 编排区块
- 组织页面级交互

约束：

- 页面不直接散落复杂 fetch 细节
- 页面不直接长期持有跨区块业务状态

### 5.3 Component 层

职责：

- 渲染可复用 UI 模块
- 承担局部交互

约束：

- 不直接拥有跨页面业务状态
- 不直接耦合后端接口

### 5.4 Composable 层

职责：

- 管理页面状态
- 管理筛选、选择、表单和动作
- 承担副作用和写回逻辑

约束：

- composable 负责“状态与动作”，不负责大段静态页面壳

### 5.5 Service 层

职责：

- 承接接口访问
- 统一处理前后端契约
- 承接本地回退或桥接逻辑

约束：

- 页面和组件不得直接散落网络请求细节

## 6. 主题标准

- 主题源应优先单独沉淀到独立目录，并明确依赖 `/Users/showfolder/Documents/workSpace/SELF/SELTEMPLATE/SELTHEME`。
- 业务工程可以消费主题变量和组件样式，但不应把主题定义只埋在某个页面里。
- 主题至少应包含：
  - 颜色变量
  - 玻璃材质变量
  - 阴影变量
  - 按钮 / 输入 / 卡片 / 标签样式
  - 背景图片或光效资产

### 6.1 主题组件分层结构

若主题已经从“少量样式片段”演进为正式主题包，则组件样式不得长期堆在一个大文件中，应优先采用“聚合入口 + 组件分层文件”的结构。

推荐结构：

```text
themes/<theme-name>/
├─ tokens.css
├─ components.css
├─ components/
│  ├─ buttons.css
│  ├─ forms.css
│  └─ overlays.css
├─ assets/
└─ preview/
   ├─ index.html
   └─ demo.html
```

分层职责：

- `tokens.css`：只放颜色、材质、阴影、圆角、模糊等主题变量。
- `components.css`：只作为聚合入口，统一 `@import` 分层组件文件，并保留少量页面骨架或全局共享布局。
- `components/buttons.css`：放胶囊按钮、图标按钮、按钮组等点击类组件。
- `components/forms.css`：放输入框、建议面板、复选框、开关、列表交互等表单与选择类组件。
- `components/overlays.css`：放气泡提示、统计卡、升级卡、展示浮层、响应式展示区等展示与浮层类组件。

约束：

- `preview/index.html` 与 `preview/demo.html` 应优先只引用 `components.css` 这个聚合入口，禁止把多个分层 CSS 散着直接挂到页面里。
- 若后续继续扩展主题控件，应先判断属于 `buttons / forms / overlays` 哪一层，再进入对应文件；不要把新控件重新堆回聚合入口。
- 若主题包仍只有极少量样式，允许暂时单文件；一旦进入可复用主题包阶段，就应升级到上述分层结构。

## 7. 测试标准

- 每次结构改动后必须先做构建验证。
- 页面改动后必须做真实页面验证。
- 视觉或交互问题不能只靠构建通过判定完成。
- 若页面支持后端联调，应优先补页面结合验证。
- 若页面通过启动器承接本地联调，则测试标准还必须覆盖启动器自身，而不是只测页面渲染结果。

## 8. 自动 bug 修复接入目标

- 页面边界清晰
- 服务边界清晰
- 测试入口稳定
- 主题和布局可视验证可回放
- 文档与代码目录保持一致
