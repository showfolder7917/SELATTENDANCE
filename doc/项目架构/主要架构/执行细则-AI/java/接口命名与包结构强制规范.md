# SELSP 接口命名与包结构强制规范

## 1. 文档定位

本文档用于统一 `SELATTENDANCE/SELSP` 所有 Java 模块的接口命名、类命名和包结构规范。

当前唯一正式参照模块是：

- `/Users/showfolder/Documents/workSpace/SELF/SELATTENDANCE/SELSP/src/main/java/com/sp/selfsp/attendance`
- 新模块命名、包结构和子域拆分必须优先参照 `attendance`
- 禁止再以 `SELTEMPLATE` 中的旧示例作为当前项目实现基线

目标是避免：

- 不同模块命名风格漂移
- 目录与包名不一致
- 一个类承担多种职责
- 后续自动检索、自动测试、自动修复时无法稳定定位代码

## 2. 包结构强制规范

### 2.1 基础包

统一根包：

```text
com.sp.selfsp
```

### 2.2 模块包

业务模块统一放在：

```text
com.sp.selfsp.{模块名}
```

### 2.3 标准子包

默认子包结构：

```text
controller
service
service.impl
dao
domain
domain.in
domain.out
```

补充子包必须满足：

- 有明确职责
- 不和现有子包语义重叠
- 能长期复用，不是临时名字

### 2.4 common 包

公共能力统一放在：

```text
com.sp.selfsp.common
```

只允许存放：

- 通用配置
- 通用响应
- 通用异常
- 通用日志
- 通用工具

禁止存放：

- 单一业务模块专属逻辑
- 仅某个页面使用的临时代码

## 3. 接口命名规范

### 3.1 Controller 命名

统一格式：

```text
{模块语义}Controller
```

示例：

- `UserController`
- `OrderController`
- `ReportController`

禁止：

- `UserApi`
- `UserHandler`
- `UserManagerController`
- `DoSomethingController`

### 3.2 Service 命名

接口统一格式：

```text
{模块语义}Service
```

实现统一格式：

```text
{模块语义}ServiceImpl
```

禁止：

- 一个模块出现多套无边界的 `XXXManager`、`XXXHelper`、`XXXProcessor`
- 实现类名称与接口名称无语义对应

### 3.3 DAO 命名

统一格式：

```text
{模块语义}Dao
```

禁止：

- `CommonDao` 承载多个模块
- `BigDao`、`AllDao`、`BaseBusinessDao` 这种无边界命名

### 3.4 输入输出对象命名

输入对象统一格式：

```text
{模块语义}{动作语义}In
```

输出对象统一格式：

```text
{模块语义}{动作语义}Out
```

持久化或领域对象统一格式：

```text
{模块语义}{领域语义}
```

示例：

- `UserSaveIn`
- `UserLoginIn`
- `UserLoginOut`
- `OrderQueryIn`
- `OrderDetailOut`

### 3.5 配置类命名

统一格式：

```text
{模块语义}Config
{模块语义}Properties
```

示例：

- `H2TcpServerConfig`
- `SelfspProperties`

### 3.6 异常类命名

统一格式：

```text
{模块语义}Exception
{模块语义}BusinessException
```

如果使用全局统一异常，则尽量减少模块级异常种类。

## 4. 接口路径命名规范

### 4.1 路径前缀

统一前缀：

```text
/api/{资源名}
```

示例：

- `/api/users`
- `/api/orders`
- `/api/reports`

### 4.2 路径语义

要求：

- 路径名优先使用资源语义
- 动作优先交给 HTTP Method 表达
- 非资源型动作可用清晰子路径表达

示例：

- `GET /api/users`
- `GET /api/users/{id}`
- `POST /api/users`
- `PUT /api/users/{id}`
- `DELETE /api/users/{id}`
- `POST /api/users/login`

禁止：

- `/api/doUserAdd`
- `/api/getUserList`
- `/api/userManager/saveOrUpdate`

## 5. 方法命名规范

### 5.1 Controller 方法

推荐动作：

- `create`
- `update`
- `delete`
- `getById`
- `list`
- `login`
- `logout`
- `submit`
- `approve`

要求：

- 方法名直接反映 HTTP 行为或业务动作
- 不使用模糊命名

### 5.2 Service 方法

Service 方法应直接体现业务动作：

- `createOrder`
- `approveInvoice`
- `generateReport`

如果模块内语义已足够明确，也可简化为：

- `create`
- `update`
- `delete`
- `list`

### 5.3 DAO 方法

DAO 方法命名应体现数据库动作：

- `insertXxx`
- `updateXxx`
- `deleteXxx`
- `selectXxxById`
- `selectXxxList`

禁止：

- `process`
- `handle`
- `run`

## 6. 包结构与文件结构一致性

强制要求：

- 包名必须和实际目录完全一致
- 目录调整后必须同步修改 `package`
- 不允许目录和包声明错位

这是后续自动定位、自动修复和批量分析的基础要求。

## 7. 一模块一语义原则

一个模块必须围绕一个稳定领域展开。

禁止：

- 一个模块同时塞用户、订单、报表、鉴权
- 用页面名、按钮名、需求阶段名直接命名模块

如果某模块开始承载多个领域，应及时拆分。

## 8. 自动化友好要求

为了后续自动 bug 修复友好，命名和包结构必须支持：

- 快速根据日志定位模块
- 快速根据测试名定位业务边界
- 快速根据类名判断职责
- 快速按目录做批量回归和局部修复

因此不允许：

- 模糊命名
- 职责混叠
- 临时缩写
- 多套命名风格并存

## 9. 执行规则

以后新增或重构模块时：

1. 先按本文档确定模块名和目录结构。
2. 再创建 Controller、Service、DAO、Domain 文件。
3. 命名不符合本文档时，应先统一命名再继续扩展。

如果某个已有旧模块与本文档不一致，后续重构时应逐步对齐，不再继续放大旧风格差异。
