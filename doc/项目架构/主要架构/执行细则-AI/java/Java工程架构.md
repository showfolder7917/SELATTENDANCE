# SELSP Java工程架构标准

## 1. 文档定位

本文档是 `SELATTENDANCE/SELSP` 后续所有 Java 后端框架方案的通用架构标准。

当前唯一正式主参照不是 `SELTEMPLATE`，而是：

- `/Users/showfolder/Documents/workSpace/SELF/SELATTENDANCE/SELSP/src/main/java/com/sp/selfsp/attendance`
- 新模块必须优先参照 `attendance` 已落地的目录、分层、XML 和契约写法
- `SELTEMPLATE` 只作为历史模板来源，不再作为当前项目的正式实现基线

作用不是描述某一个具体业务模块，而是统一以下内容：

- 工程目标
- 目录与分层约束
- 配置规范
- 数据访问规范
- 日志规范
- 异常与响应规范
- 测试规范
- 面向自动 bug 修复的演进标准

后续新增业务模块、重构模块、扩展模块时，默认都按本文档执行。

## 2. 架构目标

SELSP 的通用 Java 框架标准应长期满足以下目标：

- 可快速新增业务模块，而不破坏既有结构
- 可统一排障、统一日志、统一测试
- 可在不同机器和环境中稳定迁移
- 可支持后续自动 bug 定位、自动回归、自动修复升级
- 可把“当前实现”“通用标准”“业务示例”明确分层，避免文档和代码都绑死在单一模块

## 3. 技术基线

当前标准技术基线如下：

- Java 21
- Spring Boot 3.5.x
- MyBatis 3.x
- H2 2.x
- JUnit 5
- MockMvc
- Logback

说明：

- 这是当前默认基线，不等于永远固定版本。
- 以后升级版本时，应优先保持整体兼容和统一，不允许不同模块随意漂移到多套技术栈。

## 4. 目录标准

推荐目录结构如下：

```text
SELSP/
├─ build.gradle
├─ settings.gradle
├─ gradle/
├─ src/
│  ├─ main/
│  │  ├─ java/com/sp/selfsp/
│  │  │  ├─ SelfspApplication.java
│  │  │  ├─ common/
│  │  │  │  ├─ config/
│  │  │  │  ├─ util/
│  │  │  │  └─ web/
│  │  │  ├─ config/
│  │  │  └─ {业务模块}/
│  │  │     ├─ controller/
│  │  │     ├─ service/
│  │  │     ├─ service/impl/
│  │  │     ├─ dao/
│  │  │     ├─ domain/
│  │  │     ├─ domain/in/
│  │  │     └─ domain/out/
│  │  └─ resources/
│  │     ├─ application.yml
│  │     ├─ logback-spring.xml
│  │     ├─ schema.sql
│  │     └─ data.sql
│  └─ test/
│     ├─ java/com/sp/selfsp/
│     └─ resources/
└─ doc/
```

目录约束：

- `common` 只放跨模块公共能力，不放具体业务逻辑。
- 业务代码必须按模块分目录，不允许把多个领域揉进一个大而全目录。
- `domain/in` 表示输入契约对象，`domain/out` 表示输出契约对象，`domain` 表示领域对象或持久化对象。
- 当一个模块已经继续拆成 `auth / bootstrap / tenant / user / role / menu` 这类稳定子域时，`domain`、`domain/in`、`domain/out` 应优先下沉到对应子域；禁止为了图省事在模块根长期挂一个大而全的 `domain` 出口类。
- 测试目录必须和主代码结构保持可追踪映射。
- `doc` 目录用于存放架构、设计、接口、实施类文档，不与运行时代码混放。

## 5. 分层标准

### 5.1 Controller 层

职责：

- 暴露 HTTP 接口
- 接收请求参数
- 返回统一响应结构
- 不直接承载核心业务逻辑

约束：

- Controller 不直接写持久化逻辑
- Controller 不直接拼接跨层异常语义
- Controller 只负责协议层收口，不负责领域决策

### 5.2 Service 层

职责：

- 承接业务编排
- 做业务校验
- 控制事务边界
- 统一组织跨 DAO 调用

约束：

- 业务规则必须优先沉淀在 Service 层
- Service 应保持“一个方法完成一个明确业务动作”
- 可复用的跨模块业务规则，应进一步下沉为公共能力，而不是散落复制

### 5.3 DAO 层

职责：

- 承接数据库访问
- 承接 SQL 与对象映射
- 保持持久化边界清晰

约束：

- DAO 按领域拆分，不允许形成单一巨型 DAO
- SQL 风格必须统一
- 主键、自增、唯一约束、索引等数据库事实应由 DAO 与 schema 保持一致
- DAO 主业务查询返回值应优先使用明确 `domain` / `domain.out` 对象，不允许长期以 `Map<String, Object>` 作为 controller、service、dao 三层之间的主契约
- `Map<String, Object>` 只允许用于窄范围技术场景，例如 JWT payload、通用元数据桥接或一次性调试结构；只要字段已经稳定进入业务接口、列表项或保存返回，就必须收敛为明确对象
- 保存后回查、列表返回、详情返回、工作台聚合等正式出参必须和 `domain.out` 保持一致，禁止因为图省事继续拼匿名 `Map`
- 重构完成后必须清理空目录和无效旧残留，避免同一业务域同时保留新旧两套结构

### 5.3.1 MyBatis XML 规范

统一要求：

- 每个列表项、详情项或稳定查询对象都应显式声明 `resultMap`
- 多个查询共用同一组字段时，必须抽取 `<sql id="...Columns">`
- `select` 优先通过 `<include refid="...Columns"/>` 复用列清单，避免同一列集在多个 SQL 中散落复制
- XML 中的字段映射优先使用数据库真实列名配合 `resultMap`，不要长期依赖 `AS "camelCase"` + `resultType="map"` 作为主路径
- `resultType="map"` 不得作为正式业务列表、详情、保存回查的默认写法；只有在短生命周期技术性结构里才允许例外
- XML 风格默认参照成熟业务模块，例如 `attendance/department/dao/mapper/AttendanceDepartmentDao.xml`

### 5.4 Common 层

职责：

- 承接公共配置
- 承接统一响应
- 承接统一异常
- 承接统一日志与请求链路能力

约束：

- `common` 只放跨模块公共标准，不放某个模块的私有实现
- 如果某个能力只服务单一模块，不应强行塞进 `common`

## 6. 配置标准

### 6.1 配置收口原则

所有通用配置必须集中管理，默认通过：

- `application.yml`
- `application-*.yml`
- `ConfigurationProperties` 类型配置类

统一收口。

### 6.2 路径原则

默认要求：

- 配置优先使用相对路径
- 代码中禁止写死机器绝对路径
- 环境差异通过配置覆盖，不通过改代码解决

适用场景：

- 日志目录
- 文档目录
- 本地缓存目录
- 导入导出目录
- 外部工具工作目录

### 6.3 环境分层原则

至少区分：

- 默认开发配置
- 测试配置
- 生产或正式部署配置

约束：

- 不同环境只允许覆盖环境差异项
- 通用业务语义不能被环境配置改坏

## 7. 数据与持久化标准

### 7.1 数据库标准

当前默认支持：

- H2 作为本地开发和测试数据库
- 可逐步扩展到其他正式数据库

### 7.2 主键策略

默认原则：

- 业务表主键优先由数据库生成
- Java 业务层不手工计算数据库主键
- 数据结构、DAO 和 Service 对主键策略必须保持一致

### 7.3 schema 与数据初始化

默认原则：

- `schema.sql` 负责结构初始化
- `data.sql` 负责最小必要种子数据
- 测试环境应能独立重建最小数据库

### 7.4 业务模块数据设计

本文档不绑定具体业务表。

以后每个业务模块设计表结构时，都应遵守：

- 字段命名统一
- 审计字段统一
- 唯一约束清晰
- 可扩展字段预留合理
- schema、DAO、Service、测试同步收口

## 8. 接口标准

### 8.1 响应结构

所有接口默认使用统一响应壳。

统一响应至少应包含：

- `code`
- `message`
- `data`

### 8.2 异常收口

所有接口异常必须经过统一异常处理器收口。

至少区分：

- 参数错误
- 业务错误
- 系统错误

约束：

- 不允许让各个 Controller 自行散落错误格式
- 不允许成功响应和失败响应使用多套风格

### 8.3 输入输出对象

建议标准：

- 输入对象放在 `domain/in`
- 输出对象放在 `domain/out`
- 若模块内部已经存在稳定子域，输入输出对象应优先落在 `子域/domain/in`、`子域/domain/out`，不要继续把互不相关的保存入参、列表出参和聚合工作台对象堆在模块根目录
- 持久化对象或领域对象放在 `domain`

目的：

- 避免一个对象同时承担请求、响应、落库三种职责
- 为后续自动化测试和自动修复保留清晰契约边界

## 9. 日志标准

### 9.1 日志目标

统一日志必须满足：

- 能定位一次请求完整链路
- 能区分访问日志、业务错误日志、系统错误日志
- 能支撑自动 bug 定位与人工排障

### 9.2 traceId 标准

所有请求链路都应具备统一 `traceId`。

要求：

- 支持从上游透传
- 上游未传时本地生成
- 日志输出统一带 `traceId`
- 响应头回写 `traceId`

### 9.3 日志输出标准

默认至少包含：

- 控制台日志
- 文件日志

文件日志默认使用相对路径，例如：

- `./logs`

### 9.4 日志分类标准

后续所有模块都按以下语义输出：

- 访问日志：请求方法、路径、状态、耗时、客户端信息
- 业务日志：关键业务动作、关键状态变化、关键失败原因
- 系统日志：异常堆栈、系统级错误、框架级失败

### 9.5 后续升级方向

后续统一按以下方向升级：

- JSON 日志
- SQL 耗时日志
- 审计日志
- 错误分类码
- traceId 到测试用例、缺陷单、修复记录的关联

## 10. 测试标准

### 10.1 基本原则

代码改动后必须做可执行验证，不能只靠阅读代码收口。

### 10.2 测试分层

至少覆盖：

- Controller / API 测试
- Service 业务测试
- DAO / SQL 测试
- 配置与启动验证

### 10.3 默认测试工具

当前默认：

- `SpringBootTest`
- `MockMvc`
- H2 隔离测试库
- JUnit 5

### 10.4 回归原则

每次新增或修改后，至少回归：

- 主路径
- 边界路径
- 相邻回归路径

### 10.5 面向自动 bug 修复的要求

以后所有模块都应逐步满足：

- 测试能直接复现问题
- 测试能证明修复生效
- 测试能证明相邻路径未被破坏

## 11. 面向自动 bug 修复的架构标准

SELSP 后续若要升级为自动 bug 修复友好框架，基础标准必须包括：

- 统一日志
- 统一异常
- 统一响应
- 可重建测试数据
- 可执行回归测试
- 清晰模块边界
- 清晰输入输出契约
- 清晰配置边界

后续演进方向：

- 接入健康检查与诊断接口
- 接入 OpenAPI 或统一接口契约输出
- 接入 CI 自动测试
- 接入错误聚类、修复建议和自动回归验证链路

## 12. 当前实现示例的使用方式

当前仓库里已经存在“用户 CRUD + 登录”的一版实现。

这版实现的定位是：

- 当前可运行示例
- 当前测试样例
- 当前日志与异常收口样例

它不是通用标准本身，只是当前标准的一次参考落地。

以后新增其他模块时，应复用它体现出的标准，而不是把“用户字段、用户表、登录接口”当成所有模块的主体模板。

## 13. 文档使用规则

以后凡是：

- 新建 Java 后端模块
- 设计新框架方案
- 扩展测试体系
- 统一日志规范
- 升级自动 bug 修复能力

都应先对照本文档。

如果某个具体业务需要更细的详细设计文档，应在本文档之上新增业务专项文档，而不是直接修改本文档去绑定某一个模块实现。
