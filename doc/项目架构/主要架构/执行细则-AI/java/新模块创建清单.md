# SELSP 新模块创建清单

## 1. 文档定位

本文档用于规范 `SELATTENDANCE/SELSP` 新增任意 Java 业务模块时的标准创建步骤。

创建新模块时，唯一正式结构参照是：

- `/Users/showfolder/Documents/workSpace/SELF/SELATTENDANCE/SELSP/src/main/java/com/sp/selfsp/attendance`
- 若 `attendance` 现有写法和旧模板冲突，以 `attendance` 当前正式收口结构为准

目标不是描述某一个业务模块，而是给出一套可重复执行的模块落地清单，确保：

- 目录结构统一
- 配置方式统一
- 接口风格统一
- 日志与异常统一
- 测试与文档统一

## 2. 适用范围

适用于以下场景：

- 新增一个全新业务模块
- 把零散能力整理成正式模块
- 把旧实现按标准重建为新模块

不适用于：

- 只改一个已有方法的小修
- 纯文档修订且不新增模块

## 3. 创建前检查

新增模块前必须先确认：

1. 模块名称是否唯一，且不会和已有模块语义重叠。
2. 模块边界是否清晰，是否真的需要独立成模块。
3. 模块是否应放在现有模块下扩展，而不是重复造轮子。
4. 是否已经定义最小输入、输出、存储和测试目标。
5. 是否已经明确当前模块属于“通用能力”还是“业务模块”。

## 4. 标准创建步骤

### 4.1 定义模块名

要求：

- 使用稳定、可读、可扩展的英文或拼音语义名
- 不使用临时缩写、需求编号、个人命名
- 名称应能反映领域，而不是当前页面或按钮动作

### 4.2 创建目录

默认目录结构：

```text
src/main/java/com/sp/selfsp/{模块名}/
├─ controller/
├─ service/
├─ service/impl/
├─ dao/
├─ domain/
├─ domain/in/
└─ domain/out/
```

按需补充：

- `config/`
- `job/`
- `event/`
- `support/`

### 4.3 定义领域对象

至少明确三类对象：

- `domain/in`：请求入参对象
- `domain/out`：响应出参对象
- `domain`：持久化对象或领域对象

禁止：

- 一个对象同时承担请求、响应、落库三种职责
- 直接把数据库对象裸返回给外部接口

### 4.4 设计接口

新增模块前，至少要先明确：

- 接口用途
- 输入边界
- 输出边界
- 错误语义
- 是否需要分页、筛选、排序、状态流转

接口设计完成后，再进入 Controller 和 Service 实现。

### 4.5 设计持久化

如果模块涉及数据库：

- 先定义表结构与约束
- 再定义 DAO 与 SQL
- 再实现 Service 业务逻辑

必须同步考虑：

- 主键策略
- 唯一约束
- 审计字段
- 可扩展字段
- 测试初始化数据

### 4.6 接入公共能力

新模块必须复用以下公共标准：

- 统一响应结构
- 统一异常处理
- 统一 traceId
- 统一日志输出
- 统一配置方式

如果模块需要新增跨模块公共能力，应优先沉淀到 `common`，而不是在模块里复制实现。

### 4.7 编写测试

至少补齐：

- Controller / API 测试
- 主路径测试
- 边界路径测试
- 异常路径测试

如果模块涉及复杂业务或数据落库，还应补：

- Service 测试
- DAO / SQL 测试
- 配置或启动验证

### 4.8 补充文档

新模块落地后，至少补以下文档之一：

- 模块专项设计文档
- 模块接口文档
- 模块实施说明

接口文档落点要求：

- `SELSP` 工程的接口文档默认放在 `doc/aip接口文档/`
- 新增或迁移接口文档时，应优先落到该目录，而不是散落在 `doc/` 根目录

如果模块只是对通用标准的一次落地，不应反向修改通用架构标准文档来承载专项细节。

## 5. 模块创建完成标准

一个新模块只有满足以下条件，才能视为创建完成：

1. 目录结构已按标准建立。
2. 输入输出对象已分层。
3. Controller / Service / DAO 职责清晰。
4. 配置未写死绝对路径。
5. 日志和异常已接入统一链路。
6. 至少有最小可执行测试。
7. 已补模块级文档或设计说明。
8. 若存在接口文档，接口文档已落到 `doc/aip接口文档/` 目录。

## 6. 常见错误

禁止以下做法：

- 直接在 `common` 下写具体业务模块
- 一个模块里塞多个领域
- 只写 Controller，不补 Service 边界
- 只写代码不补测试
- 只补业务实现，不补文档
- 直接复制旧模块后只改类名，不重做边界梳理

## 7. 推荐执行顺序

建议固定按以下顺序执行：

1. 定义模块目标和边界
2. 创建目录
3. 设计入参与出参
4. 设计表结构与 DAO
5. 实现 Service
6. 实现 Controller
7. 接入日志、异常、配置
8. 编写测试
9. 补专项文档
